# 앱 로깅 테스트 케이스

기준 스펙: [앱 로깅 스펙](../spec/client/app-logging.md)

## domain

### TC-APP-LOGGING-DOMAIN-001: 담당 종류의 로그만 남긴다

- 근거: `domain > 공통 창구와 담당 기준`
- Given: 서로 다른 종류를 담당하는 기록 수단 A와 B가 등록되어 있다.
- When: A가 담당하는 종류의 로그를 공통 창구에 전달한다.
- Then: 그 로그가 A에만 남고 B에는 남지 않는다.

### TC-APP-LOGGING-DOMAIN-002: 같은 종류를 담당하는 여러 수단에 모두 남는다

- 근거: `domain > 공통 창구와 담당 기준`
- Given: 같은 종류를 담당하는 기록 수단 두 개가 등록되어 있다.
- When: 그 종류의 로그를 공통 창구에 전달한다.
- Then: 두 기록 수단 모두에 같은 로그가 남는다.

### TC-APP-LOGGING-DOMAIN-003: 어느 수단도 담당하지 않는 로그는 오류 없이 무시된다

- 근거: `domain > 공통 창구와 담당 기준`
- Given: 특정 종류만 담당하는 기록 수단이 등록되어 있다.
- When: 어느 수단도 담당하지 않는 종류의 로그를 공통 창구에 전달한다.
- Then: 어느 기록 수단에도 로그가 남지 않고, 전달은 오류 없이 완료된다.

### TC-APP-LOGGING-DOMAIN-004: 등록 전에 발생한 로그는 전달되지 않는다

- 근거: `domain > 기록 수단 등록`
- Given: 기록 수단이 아직 등록되지 않았다.
- When: 그 수단이 담당하는 종류의 로그를 공통 창구에 전달한 뒤 수단을 등록한다.
- Then: 등록 이후에도 앞서 전달한 로그는 그 수단에 남지 않는다.

### TC-APP-LOGGING-DOMAIN-006: 같은 수단을 중복 등록해도 로그가 중복으로 남지 않는다

- 근거: `domain > 기록 수단 등록`
- Given: 하나의 기록 수단을 두 번 등록했다.
- When: 그 수단이 담당하는 종류의 로그를 공통 창구에 한 번 전달한다.
- Then: 그 수단에 로그가 한 번만 남는다.

### TC-APP-LOGGING-DOMAIN-008: 한 수단의 실패가 다른 수단의 기록을 막지 않는다

- 근거: `domain > 로깅과 사용자 기능의 분리`
- Given: 로그를 남길 때마다 실패하는 기록 수단과 정상 동작하는 기록 수단이 함께 등록되어 있고, 두 수단 모두 같은 종류를 담당한다.
- When: 그 종류의 로그를 공통 창구에 전달한다.
- Then: 정상 동작하는 수단에는 로그가 남고, 전달은 오류 없이 완료된다.

### TC-APP-LOGGING-DOMAIN-009: 순서대로 발생한 로그는 순서대로 남는다

- 근거: `domain > 로깅과 사용자 기능의 분리`
- Given: 모든 종류를 담당하는 기록 수단이 등록되어 있다.
- When: 하나의 흐름에서 로그 여러 개를 순서대로 공통 창구에 전달한다.
- Then: 그 수단에 로그가 전달한 순서대로 남는다.

### TC-APP-LOGGING-DOMAIN-010: 콘솔 기록은 모든 종류의 로그를 읽을 수 있는 글로 남긴다

- 근거: `domain > 콘솔 기록`
- Given: 콘솔 기록 수단이 등록되어 있다.
- When: 콘솔 로그가 아닌 종류의 로그를 공통 창구에 전달한다.
- Then: 기본 출처 이름과 로그 내용이 사람이 읽을 수 있는 글로 개발 콘솔에 남는다.

### TC-APP-LOGGING-DOMAIN-011: 콘솔 로그의 출처 이름, 메시지, 오류 정보가 함께 남는다

- 근거: `domain > 콘솔 기록`
- Given: 콘솔 기록 수단이 등록되어 있다.
- When: 출처 이름, 메시지, 오류 정보를 지정한 콘솔 로그를 공통 창구에 전달한다.
- Then: 지정한 출처 이름, 메시지와 오류 내용이 개발 콘솔에 함께 남는다.

### TC-APP-LOGGING-DOMAIN-012: 출처 이름을 지정하지 않으면 로그를 남긴 위치의 이름이 출처 이름으로 남는다

- 근거: `domain > 콘솔 기록`
- Given: 콘솔 기록 수단이 등록되어 있다.
- When: 출처 이름과 오류 정보를 지정하지 않은 콘솔 로그를 공통 창구에 전달한다.
- Then: 로그를 남긴 앱 내부 위치의 이름이 출처 이름으로, 메시지가 오류 없이 개발 콘솔에 남는다.

### TC-APP-LOGGING-DOMAIN-013: 오류를 수집할 수 없는 플랫폼에서는 오류 보고가 남지 않는다

- 근거: `domain > 오류 보고 기록`
- Given: 오류 보고 기록 수단이 등록되어 있고, 실행 중인 플랫폼은 Firebase Crashlytics가 오류를 수집할 수 없는 플랫폼이다.
- When: 오류 정보와 메시지를 지정한 오류 보고 로그를 공통 창구에 전달한다.
- Then: 어디에도 오류 보고가 남지 않고, 전달은 오류 없이 완료된다.

### TC-APP-LOGGING-DOMAIN-014: 원격 분석을 기록할 수 없는 플랫폼에서는 원격 분석이 남지 않는다

- 근거: `domain > 원격 분석 기록`
- Given: 원격 분석 기록 수단이 등록되어 있고, 실행 중인 플랫폼은 Google Analytics 4로 기록할 수 없는 플랫폼이다.
- When: 원격 분석 로그를 공통 창구에 전달한다.
- Then: 어디에도 원격 분석이 남지 않고, 전달은 오류 없이 완료된다.

### TC-APP-LOGGING-DOMAIN-015: 원격 분석 로그에는 앞에서부터 값 25개까지만 담는다

- 근거: `domain > 원격 분석 기록`
- Given: 원격 분석 로그에 테스트 데이터의 값들이 순서대로 담겨 있다.
- When: 그 로그를 원격 분석으로 남길 형태로 바꾼다.
- Then: 테스트 데이터의 결과대로 값이 담긴다.
- 테스트 데이터:

| 로그의 값 | 결과 |
| --- | --- |
| 값 25개 | 25개 모두 담긴다 |
| 값 26개 | 앞의 25개만 담기고 26번째 값은 담기지 않는다 |
| 빈 값 1개 뒤에 값 25개 | 빈 값을 뺀 25개가 모두 담긴다 |

### TC-APP-LOGGING-DOMAIN-016: 원격 분석 값의 이름과 글 값을 길이 한도에 맞춘다

- 근거: `domain > 원격 분석 기록`
- Given: 원격 분석 로그에 테스트 데이터의 이름이나 글 값이 담겨 있다.
- When: 그 로그를 원격 분석으로 남길 형태로 바꾼다.
- Then: 테스트 데이터의 결과대로 남는다.
- 테스트 데이터:

| 로그의 이름·값 | 결과 |
| --- | --- |
| 40자인 이름 | 40자 이름 그대로 남는다 |
| 41자인 이름 | 앞 40자 이름으로 남는다 |
| 100자인 글 값 | 100자 값 그대로 남는다 |
| 101자인 글 값 | 앞 100자 값으로 남는다 |

### TC-APP-LOGGING-DOMAIN-017: 원격 분석 로그의 빈 값은 담지 않는다

- 근거: `domain > 원격 분석 기록`
- Given: 원격 분석 로그에 값이 아예 없는 빈 값, 내용이 없는 글, 내용이 있는 글이 함께 담겨 있다.
- When: 그 로그를 원격 분석으로 남길 형태로 바꾼다.
- Then: 빈 값은 담기지 않고, 내용이 없는 글은 빈 글로, 내용이 있는 글은 그대로 담긴다.

### TC-APP-LOGGING-DOMAIN-018: 원격 분석 값의 종류를 지켜 남긴다

- 근거: `domain > 원격 분석 기록`
- Given: 원격 분석 로그에 테스트 데이터의 값이 담겨 있다.
- When: 그 로그를 원격 분석으로 남길 형태로 바꾼다.
- Then: 각 값이 테스트 데이터의 결과로 남는다.
- 테스트 데이터:

| 로그의 값 | 결과 |
| --- | --- |
| 정수 `34` | 숫자 `34` |
| 소수 `1.5` | 숫자 `1.5` |
| 숫자처럼 보이는 글 `"1617893780"` | 글 `1617893780` |
| 참 | 글 `true` |
| 거짓 | 글 `false` |

### TC-APP-LOGGING-DOMAIN-019: 여러 값을 묶은 값은 한 줄의 글로 바꿔 길이 한도에 맞춘다

- 근거: `domain > 원격 분석 기록`
- Given: 원격 분석 로그에 테스트 데이터의 묶은 값이 담겨 있다.
- When: 그 로그를 원격 분석으로 남길 형태로 바꾼다.
- Then: 테스트 데이터의 결과대로 한 줄의 글로 남는다.
- 테스트 데이터:

| 로그의 값 | 결과 |
| --- | --- |
| 한 줄의 글로 바꿨을 때 100자 이하인 묶은 값 | 묶은 내용을 담은 한 줄의 글 그대로 남는다 |
| 한 줄의 글로 바꿨을 때 100자를 넘는 묶은 값 | 그 글의 앞 100자로 남는다 |

## 작성하지 않는 이유

- `domain > 기록 수단 등록`의 앱 재실행 시 등록 초기화: 앱 종료와 재시작이 필요해 유닛 테스트로 결정적으로 검증할 수 없다. 시작 시점 등록 자체는 앱 초기화 구성으로 다룬다. 앱 프로세스를 띄우고 끝낸 뒤 다시 띄울 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 콘솔 기록`의 플랫폼·빌드 종류별 등록 기준: 빌드 종류별 앱 초기화 구성의 차이는 실제 빌드 산출물 확인이 필요해 유닛 테스트로 검증할 수 없다. 빌드 종류마다 산출물을 만들어 실행하고 등록된 기록 수단을 확인할 수 있는 빌드 검증 환경이 갖춰지면 자동화한다.
- `domain > 콘솔 기록`의 플랫폼별 콘솔 출력 수단(Android Logcat, iOS 콘솔)과 iOS·웹의 기본 출처 이름 사용: 해당 플랫폼에서의 실행이 필요해 현재 유닛 테스트 환경(데스크톱 앱 환경)에서는 검증할 수 없다. 콘솔 출력 내용은 데스크톱 앱의 콘솔로 검증한다. Android·iOS·웹 실행 환경에서 테스트를 돌리고 그 플랫폼의 콘솔 출력을 읽을 수 있게 되면 자동화한다.
- `domain > 로깅과 사용자 기능의 분리`의 동시 발생 로그 순서: 스펙이 순서를 정하지 않으므로 판정할 기대 결과가 없다. 스펙이 동시에 발생한 로그의 순서를 정하면 그 기준으로 자동화한다.
- `domain > 오류 보고 기록`의 Android·iOS에서 오류 보고가 Firebase Crashlytics에 남는지: 해당 플랫폼 실행 환경과 실제 Firebase 프로젝트가 필요해 현재 유닛 테스트 환경(데스크톱 앱 환경)에서는 검증할 수 없다. Android·iOS 실행 환경과 결과를 조회할 수 있는 테스트용 Firebase 프로젝트가 갖춰지면 자동화한다.
- `domain > 오류 보고 기록`의 Firebase Crashlytics를 사용할 준비가 되지 않은 빌드: 준비 여부는 Android·iOS 빌드에 Firebase 설정이 들어 있는지로 정해져, 현재 유닛 테스트 환경(데스크톱 앱 환경)에서는 그런 빌드를 만들 수 없다. 기록 수단 하나가 실패해도 전달이 오류 없이 끝나고 다른 수단의 기록이 막히지 않는 것은 TC-APP-LOGGING-DOMAIN-008이 덮는다. Firebase 설정을 뺀 Android·iOS 빌드를 실행해 사용자 행동이 끝까지 완료되는지 확인할 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 오류 보고 기록`의 전송 시점과 앱 재실행 후 전송: 전송 시점을 Firebase Crashlytics가 정하므로 앱에서 제어하거나 관찰할 수 있는 결과가 없다. Firebase Crashlytics의 전송을 가로채 시점을 관찰할 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 오류 보고 기록`의 앱이 종료되는 오류 자동 수집: 앱 종료가 필요해 유닛 테스트로 결정적으로 검증할 수 없다. Android·iOS에서 앱을 강제로 종료시키고 다시 실행한 뒤 수집 결과를 조회할 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 오류 보고 기록`의 빌드 종류와 무관한 등록: 빌드 종류별 앱 초기화 구성의 차이는 실제 빌드 산출물 확인이 필요해 유닛 테스트로 검증할 수 없다. 빌드 종류마다 산출물을 만들어 실행하고 등록된 기록 수단을 확인할 수 있는 빌드 검증 환경이 갖춰지면 자동화한다.
- `domain > 로그 내용 제한`: 민감한 값을 담지 않는 것은 로그를 정의할 때 지킬 작성 지침으로, 공통 창구의 동작으로 관찰할 수 없다. 로그를 정의하는 곳마다 담는 값을 검사할 수 있는 정적 검사 규칙이 갖춰지면 자동화한다.
- `domain > 원격 분석 기록`의 Android·iOS에서 원격 분석이 Google Analytics 4에 남는지: 해당 플랫폼 실행 환경과 실제 Google Analytics 4 속성이 필요해 현재 유닛 테스트 환경(데스크톱 앱 환경)에서는 검증할 수 없다. Android·iOS 실행 환경과 결과를 조회할 수 있는 테스트용 Google Analytics 4 속성이 갖춰지면 자동화한다.
- `domain > 원격 분석 기록`의 Google Analytics 4를 사용할 준비가 되지 않은 빌드: 준비 여부는 Android·iOS 빌드에 Firebase 설정이 들어 있는지로 정해져, 현재 유닛 테스트 환경(데스크톱 앱 환경)에서는 그런 빌드를 만들 수 없다. 기록 수단 하나가 실패해도 전달이 오류 없이 끝나고 다른 수단의 기록이 막히지 않는 것은 TC-APP-LOGGING-DOMAIN-008이 덮는다. Firebase 설정을 뺀 Android·iOS 빌드를 실행해 사용자 행동이 끝까지 완료되는지 확인할 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 원격 분석 기록`의 플랫폼 자동 수집 미사용: 플랫폼이 제공하는 자동 수집을 끄는 것은 실제 빌드 산출물과 플랫폼 실행 환경 확인이 필요해 유닛 테스트로 검증할 수 없다. Android·iOS 빌드 산출물을 실행하고 Google Analytics 4로 나가는 사건을 가로채 볼 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 원격 분석 기록`의 전송 시점과 앱 재실행 후 전송: 전송 시점을 Google Analytics 4가 정하므로 앱에서 제어하거나 관찰할 수 있는 결과가 없다. Google Analytics 4의 전송을 가로채 시점을 관찰할 수 있는 테스트 환경이 갖춰지면 자동화한다.
- `domain > 원격 분석 기록`의 빌드 종류와 무관한 등록: 빌드 종류별 앱 초기화 구성의 차이는 실제 빌드 산출물 확인이 필요해 유닛 테스트로 검증할 수 없다. 빌드 종류마다 산출물을 만들어 실행하고 등록된 기록 수단을 확인할 수 있는 빌드 검증 환경이 갖춰지면 자동화한다.
- `domain > 원격 분석 기록`의 담을 수 있는 값 제한: 로그를 정의할 때 지킬 작성 지침으로, 공통 창구의 동작으로 관찰할 수 없다. 화면 조회에 이 제한이 지켜지는지는 [화면 조회 로깅 테스트 케이스](./screen-view-logging.md)의 TC-SCREEN-VIEW-LOGGING-DOMAIN-010이 덮는다. 원격 분석 로그를 정의하는 곳마다 담는 값이 고정값인지 검사할 수 있는 정적 검사 규칙이 갖춰지면 자동화한다.
