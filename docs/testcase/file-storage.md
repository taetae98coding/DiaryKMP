# 파일 보관 테스트 케이스

기준 스펙: [파일 보관 스펙(client)](../spec/client/file-storage.md), [파일 보관 스펙(common)](../spec/common/file-storage.md), [파일 보관 스펙(server)](../spec/server/file-storage.md)

각 케이스의 `근거`는 절이 있는 스펙 폴더를 앞에 붙여 `client > domain > 절 이름`처럼 적는다.

## domain

### TC-FILE-STORAGE-DOMAIN-001: 50MB를 넘는 파일은 서버에 올리지 않고 크기 초과로 실패한다

- 근거: `client > domain > 올릴 수 있는 파일`, `common > data > 올리는 파일`
- Given: 사용자가 테스트 데이터 크기의 파일을 골랐고, 서버는 올리기 요청에 성공을 돌려준다.
- When: 그 파일로 올리기를 시작한다.
- Then: 테스트 데이터의 결과가 된다.
- 테스트 데이터:

| 파일 크기 | 결과 |
| --- | --- |
| 0바이트 | 서버에 올리고 성공한다 |
| 52,428,800바이트(50MB) | 서버에 올리고 성공한다 |
| 52,428,801바이트 | 서버에 요청하지 않고 크기 초과로 실패한다 |

### TC-FILE-STORAGE-DOMAIN-002: 올릴 때 기기가 알려 주는 파일 이름과 형식을 함께 보낸다

- 근거: `client > domain > 올릴 수 있는 파일`, `common > data > 올리는 파일`
- Given: 사용자가 기기가 테스트 데이터의 이름과 형식을 알려 주는 파일을 골랐다.
- When: 그 파일로 올리기를 시작한다.
- Then: 서버에 보낸 요청에 테스트 데이터의 이름과 보낸 형식이 담긴다.
- 테스트 데이터:

| 기기가 알려 주는 이름 | 기기가 알려 주는 형식 | 보낸 형식 |
| --- | --- | --- |
| `보고서.pdf` | `application/pdf` | `application/pdf` |
| `data.bin` | 알려 주지 않음 | 형식을 알 수 없는 일반 파일 형식 |

### TC-FILE-STORAGE-DOMAIN-003: 이름이나 크기를 알 수 없는 파일은 서버에 요청하지 않고 실패한다

- 근거: `client > domain > 올릴 수 있는 파일`, `client > data > 올리기 흐름`
- Given: 사용자가 고른 파일의 위치에서 테스트 데이터의 정보를 읽을 수 없다.
- When: 그 위치로 올리기를 시작한다.
- Then: 서버에 요청하지 않고 크기 초과가 아닌 실패로 끝난다.
- 테스트 데이터:

| 읽을 수 없는 정보 |
| --- |
| 파일 이름 |
| 파일 크기 |

### TC-FILE-STORAGE-DOMAIN-008: 내용을 읽을 수 없는 파일은 크기 초과가 아닌 실패로 끝난다

- 근거: `client > domain > 올릴 수 있는 파일`
- Given: 사용자가 고른 파일의 이름과 크기는 읽을 수 있지만, 올리는 도중 내용을 읽을 수 없다.
- When: 그 파일로 올리기를 시작한다.
- Then: 올리기가 크기 초과가 아닌 실패로 끝난다.

### TC-FILE-STORAGE-DOMAIN-004: 같은 이름의 파일을 다시 올려도 별개의 파일로 보관한다

- 근거: `client > domain > 올릴 수 있는 파일`, `server > domain > 보관하는 파일`
- Given: 계정 A가 `memo.txt` 파일을 한 번 올렸다.
- When: 계정 A가 이름이 같은 `memo.txt` 파일을 한 번 더 올리고 목록을 불러온다.
- Then: 목록에 식별자가 서로 다른 `memo.txt` 파일 두 개가 나타난다.
- 작성하지 않는 이유: 같은 이름의 파일을 따로 보관하는 것은 서버가 보관하면서 정하는 결과라 앱 경계에서는 서버가 돌려준 목록을 그대로 보여 줄 뿐이다. 자동화하려면 실제 서버에 같은 이름으로 두 번 올린 뒤 목록을 조회하는 서버 정책 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DOMAIN-005: 목록에는 그 계정이 올린 파일만 올린 시각이 늦은 순으로 나타난다

- 근거: `client > domain > 목록에 노출하는 파일`, `common > data > 목록 요청`, `server > domain > 보관하는 파일`
- Given: 계정 A와 계정 B가 각각 파일을 여러 번에 나누어 올렸다.
- When: 계정 A의 로그인 세션으로 목록을 불러온다.
- Then: 계정 A가 올린 파일만 나타나고, 올린 시각이 늦은 파일이 앞에 온다.
- 작성하지 않는 이유: 어느 계정의 파일을 어떤 순서로 돌려줄지는 서버가 정하고 앱은 받은 순서를 그대로 보여 준다. 앱이 받은 순서를 유지하는 것은 TC-FILE-HOME-FEATURE-012가 확인한다. 자동화하려면 실제 서버에 두 계정으로 파일을 올린 뒤 각 세션으로 목록을 조회하는 서버 정책 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DOMAIN-009: 올리는 중인 파일이 있으면 새 파일을 올리기 시작하지 않는다

- 근거: `client > domain > 한 번에 올리는 파일`
- Given: 파일 A를 올리는 중이고, 서버가 그 요청에 아직 응답하지 않았다.
- When: 파일 B로 올리기를 요청한다.
- Then: 파일 B는 서버에 요청되지 않고, 파일 A의 올리기는 그대로 이어지며, 올리는 중인 파일은 하나로 남는다.

### TC-FILE-STORAGE-DOMAIN-010: 올리기를 시작한 계정이 바뀌면 중단하고 결과를 알리지 않는다

- 근거: `client > domain > 올리기를 중단하는 계기`, `client > domain > 올리기 상태`
- Given: 계정 A로 파일을 올리는 중이고, 서버가 그 요청에 아직 응답하지 않았다.
- When: 계정 상태가 테스트 데이터와 같이 바뀐다.
- Then: 테스트 데이터의 결과가 된다.
- 테스트 데이터:

| 바뀐 계정 상태 | 결과 |
| --- | --- |
| 게스트 | 올리기가 중단되어 올리는 파일이 없어지고, 성공이나 실패 결과가 나오지 않는다 |
| 계정 B의 사용자 | 올리기가 중단되어 올리는 파일이 없어지고, 성공이나 실패 결과가 나오지 않는다 |
| 세션 갱신 여부만 바뀐 계정 A의 사용자 | 올리기가 이어지고, 서버가 응답하면 그 결과가 나온다 |
| 계정 상태를 확인하지 못함 | 올리기가 이어지고, 서버가 응답하면 그 결과가 나온다 |

### TC-FILE-STORAGE-DOMAIN-011: 올리는 동안 보낸 양을 백분율로 알 수 있고 백분율은 줄어들지 않는다

- 근거: `client > domain > 올리기 상태`
- Given: 크기가 1,000바이트인 파일을 올리는 중이다.
- When: 서버에 보낸 양이 차례로 0바이트, 250바이트, 1,000바이트가 된다.
- Then: 올리는 중인 파일의 백분율이 차례로 백분율 없음, 25%, 100%가 되고, 그 사이에 줄어들지 않는다.

### TC-FILE-STORAGE-DOMAIN-012: 빈 파일은 끝날 때까지 백분율 없이 올리는 중으로 보인다

- 근거: `client > domain > 올리기 상태`
- Given: 크기가 0바이트인 파일을 올리는 중이고, 서버가 아직 응답하지 않았다.
- When: 올리는 중인 파일의 진행을 확인한다.
- Then: 백분율 없이 올리는 중으로 보인다.

### TC-FILE-STORAGE-DOMAIN-014: 로그아웃하면 올리는 중이거나 다시 올릴 예정인 올리기를 모두 취소한다

- 근거: `client > domain > 올리기를 중단하는 계기`
- Given: 파일을 올리는 중이거나, 시스템이 이어 올리는 파일이 있다.
- When: 계정 상태가 테스트 데이터와 같이 바뀐다.
- Then: 테스트 데이터의 결과가 된다.
- 테스트 데이터:

| 바뀐 계정 상태 | 결과 |
| --- | --- |
| 게스트(로그아웃) | 올리기가 취소되어 결과를 알리지 않고, 붙들어 둔 파일을 놓는다 |
| 세션 갱신 여부만 바뀐 같은 계정의 사용자 | 올리기가 계속된다 |

### TC-FILE-STORAGE-DOMAIN-015: Android에서 다시 올릴 예정인 파일은 로그아웃하면 올리지 않는다

- 근거: `client > domain > 올리기를 중단하는 계기`
- Given: Android에서 시스템이 앱을 정리해 같은 파일을 다시 올리려고 기다리는 중이다.
- When: 사용자가 로그아웃해 계정 상태가 게스트가 된다.
- Then: 그 파일은 다시 올리지 않고 올리기가 취소되며, 붙들어 둔 파일을 놓는다.

## data

### TC-FILE-STORAGE-DATA-001: 처음 불러올 때 마지막 파일 없이 20개를 요청한다

- 근거: `client > data > 목록 불러오기`, `common > data > 목록 요청`
- Given: 아직 불러온 파일이 없다.
- When: 목록을 처음 불러온다.
- Then: 서버에 가져올 개수 20과 마지막 파일 없음을 담은 목록 요청을 한 번 보낸다.

### TC-FILE-STORAGE-DATA-002: 이어서 불러올 때 이미 받은 마지막 파일을 기준으로 20개를 요청한다

- 근거: `client > data > 목록 불러오기`, `common > data > 목록 요청`
- Given: 첫 요청으로 파일 20개를 받았다.
- When: 목록을 이어서 불러온다.
- Then: 서버에 가져올 개수 20과, 받은 20개 중 마지막 파일의 올린 시각과 식별자를 담은 목록 요청을 보낸다.

### TC-FILE-STORAGE-DATA-003: 돌려받은 파일이 20개보다 적으면 더 요청하지 않는다

- 근거: `client > data > 목록 불러오기`
- Given: 서버가 목록 요청에 테스트 데이터 개수의 파일을 돌려준다.
- When: 목록을 처음 불러온 뒤 목록의 끝에 다가간다.
- Then: 테스트 데이터의 결과가 된다.
- 테스트 데이터:

| 돌려받은 파일 수 | 결과 |
| --- | --- |
| 20개 | 다음 20개를 이어서 요청한다 |
| 19개 | 더 요청하지 않는다 |
| 0개 | 더 요청하지 않는다 |

### TC-FILE-STORAGE-DATA-004: 불러오기에 실패해도 이미 불러온 파일은 남고 스스로 다시 요청하지 않는다

- 근거: `client > data > 목록 불러오기`
- Given: 첫 요청으로 파일 20개를 받았고, 서버가 다음 요청에 실패를 돌려준다.
- When: 목록을 이어서 불러온다.
- Then: 이어서 불러오기가 실패로 끝나고, 이미 받은 20개는 그대로 남으며, 사용자가 다시 시도하기 전까지 같은 요청을 다시 보내지 않는다.

### TC-FILE-STORAGE-DATA-005: 고른 파일의 내용을 그대로 올리고 서버가 돌려준 파일 정보를 받는다

- 근거: `client > data > 올리기 흐름`, `common > data > 올리는 파일`, `common > data > 파일 정보`
- Given: 사용자가 내용이 정해진 파일을 골랐고, 서버가 올리기 요청에 파일 정보를 돌려준다.
- When: 그 파일로 올리기를 시작한다.
- Then: 서버에 보낸 내용과 알린 크기가 고른 파일의 내용·크기와 같고, 올리기가 성공해 서버가 돌려준 식별자, 이름, 형식, 크기, 올린 시각을 가진 파일 정보가 결과로 나온다.

### TC-FILE-STORAGE-DATA-006: 서버가 크기 초과로 거절하면 크기 초과 실패로 구분한다

- 근거: `server > data > 받는 파일`, `client > data > 올리기 흐름`, `client > domain > 올릴 수 있는 파일`
- Given: 사용자가 50MB 이하의 파일을 골랐고, 서버가 올리기 요청에 테스트 데이터의 응답을 돌려준다.
- When: 그 파일로 올리기를 시작한다.
- Then: 테스트 데이터의 결과로 올리기가 실패한다.
- 테스트 데이터:

| 서버 응답 | 결과 |
| --- | --- |
| 크기 초과 거절 | 크기 초과 실패 |
| 파일 이름이 약속에 맞지 않아 잘못된 요청으로 거절 | 크기 초과가 아닌 실패 |
| 그 밖의 실패 | 크기 초과가 아닌 실패 |

### TC-FILE-STORAGE-DATA-007: 중단하기 전에 서버가 끝까지 받은 파일만 보관된다

- 근거: `client > domain > 올리기를 중단하는 계기`
- Given: 파일을 올리는 중이다.
- When: 올리기를 시작한 계정이 다른 계정으로 바뀌어 올리기가 중단된다.
- Then: 서버가 끝까지 받은 경우에만 파일이 보관되어 다음 목록에 나타난다.
- 작성하지 않는 이유: 중단 시점에 서버가 파일을 끝까지 받았는지는 실제 네트워크 전송과 서버 처리 시점에 달려 있어 반복 실행으로 같은 결과를 판정할 수 없다. 앱이 중단하고 결과를 기다리지 않는 것은 TC-FILE-STORAGE-DOMAIN-010이 확인한다. 자동화하려면 전송 도중 연결을 끊는 시점을 제어할 수 있는 서버 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-008: 서버는 약속을 어긴 올리기 요청을 거절한다

- 근거: `server > data > 받는 파일`
- Given: 테스트 데이터의 올리기 요청이 있다.
- When: 그 요청을 서버에 보낸다.
- Then: 서버는 파일을 보관하지 않고 테스트 데이터의 거절을 돌려준다.
- 테스트 데이터:

| 요청 | 거절 |
| --- | --- |
| 로그인하지 않은 요청 | 인증 실패 |
| 이름이 비어 있는 요청 | 잘못된 요청 |
| 이름이 공백만으로 된 요청 | 잘못된 요청 |
| 이름이 256자인 요청 | 잘못된 요청 |
| 크기가 50MB를 넘는 요청 | 크기 초과 |
| 이름이 약속에 맞지 않고 크기도 50MB를 넘는 요청 | 잘못된 요청 |

- 작성하지 않는 이유: 요청을 검증하고 거절하는 것은 서버의 처리라 앱 경계에서 관찰할 수 없다. 자동화하려면 서버 함수에 직접 요청을 보내 응답을 확인하는 서버 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-009: 파일 정보를 등록하지 못하면 보관한 파일 내용을 남기지 않는다

- 근거: `server > data > 보관 순서`
- Given: 서버가 파일 내용은 보관하지만 파일 정보를 등록하지 못하도록 설정되어 있다.
- When: 파일을 올린다.
- Then: 올리기가 실패하고, 서버 보관 공간에 그 파일 내용이 남지 않으며, 목록에도 나타나지 않는다.
- 작성하지 않는 이유: 등록 실패와 되돌리기는 서버가 한 요청 안에서 처리하는 결과라, 앱은 실패 응답만 받아 다른 실패와 구분할 수 없다. 자동화하려면 실제 서버 보관 공간에서 등록 단계가 실패하도록 설정하고 남은 파일을 조회하는 수단이 필요하다.

### TC-FILE-STORAGE-DATA-010: 계정이 삭제되면 그 계정의 파일이 목록에 나타나지 않는다

- 근거: `server > domain > 보관하는 파일`
- Given: 계정 A가 파일을 올려 두었다.
- When: 계정 A가 삭제된다.
- Then: 계정 A의 파일 정보가 함께 삭제되어 어떤 목록 요청에도 나타나지 않는다.
- 작성하지 않는 이유: 계정 삭제와 함께 파일 정보를 지우는 것은 서버 저장소가 보장하는 결과라 앱 경계에서 관찰할 수 없고, 앱에는 계정을 삭제하는 수단도 없다. 자동화하려면 실제 서버에서 계정을 삭제한 뒤 파일 정보를 조회하는 서버 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-011: 서버는 약속을 어긴 목록 요청을 거절한다

- 근거: `server > data > 목록 응답`, `common > data > 목록 요청`
- Given: 테스트 데이터의 목록 요청이 있다.
- When: 그 요청을 서버에 보낸다.
- Then: 서버는 목록을 돌려주지 않고 잘못된 요청으로 거절한다.
- 테스트 데이터:

| 요청 |
| --- |
| 가져올 개수가 0개인 요청 |
| 가져올 개수가 101개인 요청 |
| 마지막 파일의 올린 시각이 시각 형식이 아닌 요청 |
| 마지막 파일의 식별자가 식별자 형식이 아닌 요청 |

- 작성하지 않는 이유: 요청을 검증하고 거절하는 것은 서버의 처리이고, 앱은 언제나 약속을 지킨 요청만 보내므로 앱 경계에서 관찰할 수 없다. 자동화하려면 서버 함수에 직접 요청을 보내 응답을 확인하는 서버 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-012: 형식 정보가 없는 파일은 일반 파일로 보관한다

- 근거: `server > data > 받는 파일`
- Given: 형식 정보 없이 보낸 올리기 요청이 있다.
- When: 그 요청을 서버에 보낸다.
- Then: 파일이 보관되고, 돌려받은 파일 정보의 형식은 형식을 알 수 없는 일반 파일 형식이다.
- 작성하지 않는 이유: 앱은 형식을 모를 때도 일반 파일 형식을 채워 보내므로(TC-FILE-STORAGE-DOMAIN-002) 형식 정보 없는 요청을 만들지 않는다. 서버가 빈 형식을 채우는 결과는 서버 함수에 직접 요청을 보내야 확인할 수 있어, 자동화하려면 서버 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-013: 올리기가 오래 걸려도 앱이 시간을 이유로 끝내지 않는다

- 근거: `client > data > 올리기 흐름`
- Given: 서버가 올리기 요청에 30분 동안 응답하지 않다가 파일 정보를 돌려준다.
- When: 파일 하나로 올리기를 시작한다.
- Then: 앱이 그동안 올리기를 실패로 끝내지 않고, 서버가 응답하면 올리기가 성공한다.

### TC-FILE-STORAGE-DATA-015: iOS에서 연결이 없거나 끊기면 시스템의 판단에 따라 기다리거나 실패한다

- 근거: `client > data > 연결이 없을 때`
- Given: iOS 기기가 네트워크에 연결되어 있지 않거나 올리는 도중 연결이 끊긴다.
- When: 파일 하나로 올리기를 시작한다.
- Then: 연결될 때까지 올리는 중으로 기다렸다가 올리고, 시스템이 포기하면 실패로 끝난다.
- 작성하지 않는 이유: 연결을 기다리고 다시 이어 올릴지는 iOS 시스템의 전송 수단이 정하므로, 시스템 없이 반복 실행해 같은 결과를 판정할 수 없다. 자동화하려면 iOS 기기에서 네트워크 연결을 끊고 잇는 시점을 제어할 수 있는 기기 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-016: 앱이 화면 뒤로 가거나 정리되어도 플랫폼별 범위에서 올리기가 이어진다

- 근거: `client > data > 올리기 진행 유지 범위`
- Given: 파일을 올리는 중이다.
- When: 테스트 데이터의 일이 일어난다.
- Then: 테스트 데이터의 결과가 된다.
- 테스트 데이터:

| 플랫폼 | 일어난 일 | 결과 |
| --- | --- | --- |
| Android | 앱이 화면 뒤로 간다 | 계속 올린다 |
| Android | 시스템이 앱을 정리한다 | 앱이 다시 살아나면 같은 파일을 처음부터 다시 올린다 |
| Android | 시스템 설정에서 앱을 강제로 멈춘 뒤 다시 실행한다 | 같은 파일을 처음부터 다시 올린다 |
| iOS | 앱이 화면 뒤로 가거나 시스템이 앱을 정리한다 | 시스템이 계속 올리고 결과를 알린다 |
| iOS | 앱 전환기에서 앱을 종료한다 | 올리기가 중단된다 |
| 데스크톱 앱, 웹 | 앱이나 탭을 종료한다 | 올리기가 중단된다 |

- 작성하지 않는 이유: 앱을 화면 뒤로 보내고, 시스템이 앱을 정리하고, 앱을 강제로 멈추는 일은 운영체제가 일으키는 실행 경계라 테스트 환경에서 결정적으로 재현할 수 없다. FileHome 화면을 떠나도 올리기가 이어지는 것은 TC-FILE-STORAGE-DATA-024가 확인한다. 자동화하려면 각 플랫폼에서 앱의 실행 상태를 바꿀 수 있는 기기 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-017: 올리기가 끝나면 기기에 임시로 둔 사본을 남기지 않는다

- 근거: `client > data > 기기에 두는 것`
- Given: iOS나 웹에서 사용자가 고른 파일을 앱이 올리기 위해 기기에 임시 사본으로 두었다.
- When: 올리기가 성공, 실패, 중단 중 하나로 끝난다.
- Then: 그 임시 사본이 기기에 남지 않는다.
- 작성하지 않는 이유: 임시 사본은 iOS의 앱 보관 공간과 브라우저가 관리하는 파일 주소에만 생기므로, 저장소의 테스트 환경에서는 그 사본이 남았는지 관찰할 수 없다. 자동화하려면 iOS 기기의 앱 보관 공간과 브라우저의 파일 주소를 조회할 수 있는 기기·브라우저 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-018: 앞선 실행에서 이어 올리는 파일은 올리는 중인 파일로 보고, 끝나면 결과를 알린다

- 근거: `client > data > 올리기 진행 유지 범위`, `client > domain > 한 번에 올리는 파일`
- Given: 앱이 다시 시작되었고, 기기의 시스템이 앞선 실행에서 시작한 파일을 이어서 올리는 중이다.
- When: 새 파일로 올리기를 요청한 뒤, 이어 올리던 파일의 올리기가 테스트 데이터의 결과로 끝난다.
- Then: 이어 올리는 동안 올리는 중인 파일이 있는 것으로 보여 새 파일은 서버에 요청되지 않고, 끝나면 테스트 데이터의 결과가 알려진다.
- 테스트 데이터:

| 결과 |
| --- |
| 성공 |
| 크기 초과로 실패 |
| 그 밖의 이유로 실패 |

### TC-FILE-STORAGE-DATA-020: 데스크톱 앱과 웹에서 연결이 없으면 올리기가 실패로 끝난다

- 근거: `client > data > 연결이 없을 때`
- Given: 데스크톱 앱이나 웹에서 네트워크에 연결되어 있지 않아 서버 요청이 연결 실패로 끝난다.
- When: 파일 하나로 올리기를 시작한다.
- Then: 기다리지 않고 크기 초과가 아닌 실패로 끝나며, 올리는 파일이 없는 상태로 돌아간다.

### TC-FILE-STORAGE-DATA-021: Android에서 연결 문제로 보내지 못하면 다시 시도하지 않고 실패로 끝난다

- 근거: `client > data > 연결이 없을 때`
- Given: Android에서 서버 요청이 테스트 데이터의 때에 연결 문제로 끝난다.
- When: 파일 하나로 올리기를 요청한다.
- Then: 요청하자 곧바로 올리기가 시작되고, 연결 문제가 생기면 크기 초과가 아닌 실패로 끝나며, 같은 파일을 다시 올리지 않는다.
- 테스트 데이터:

| 연결 문제가 생기는 때 |
| --- |

| 올리는 도중 |

### TC-FILE-STORAGE-DATA-022: Android에서 고른 파일을 붙들어 둘 수 없으면 올리지 않고 실패한다

- 근거: `client > data > 기기에 두는 것`
- Given: Android에서 사용자가 고른 파일을 제공하는 앱이 그 파일을 계속 읽을 수 있게 붙들어 두는 것을 허용하지 않는다.
- When: 그 파일로 올리기를 요청한다.
- Then: 서버에 올리지 않고 크기 초과가 아닌 실패로 끝나며, 올리는 파일이 없는 상태로 남는다.

### TC-FILE-STORAGE-DATA-023: 올리기가 끝나면 붙들어 둔 파일을 놓고, 다시 올릴 예정이면 붙들어 둔다

- 근거: `client > data > 기기에 두는 것`
- Given: 사용자가 고른 파일을 올리는 중이라 앱이 그 파일을 붙들어 두고 있다.
- When: 테스트 데이터의 일로 이번 올리기가 멈춘다.
- Then: 테스트 데이터의 결과가 되고, 사용자가 고른 원본 파일은 지워지거나 바뀌지 않는다.
- 테스트 데이터:

| 일어난 일 | 결과 |
| --- | --- |
| 올리기가 성공한다 | 붙들어 둔 파일을 놓는다 |
| 올리기가 실패한다 | 붙들어 둔 파일을 놓는다 |
| 계정이 바뀌어 올리기가 중단된다 | 붙들어 둔 파일을 놓는다 |
| 시스템이 올리기를 멈추고 같은 파일을 다시 올릴 예정이다 | 붙들어 둔 파일을 그대로 둔다 |

### TC-FILE-STORAGE-DATA-024: FileHome 화면을 떠나도 올리기는 끝까지 진행되고 결과가 알려진다

- 근거: `client > data > 올리기 진행 유지 범위`
- Given: 사용자가 FileHome 화면에서 파일 올리기를 시작했고, 서버가 그 요청에 아직 응답하지 않았다.
- When: 사용자가 FileHome 화면을 떠난 뒤 서버가 성공을 돌려준다.
- Then: 올리기가 중단되지 않고 성공으로 끝나며, 그 결과가 [파일 올리기 알림 스펙](../spec/client/file-upload-notification.md)에 따라 알림으로 알려진다.

### TC-FILE-STORAGE-DATA-025: 서버 실행 시간 안에 파일을 끝까지 받지 못하면 보관하지 않는다

- 근거: `server > data > 받는 파일`
- Given: 서버 함수가 허용하는 실행 시간 안에 끝까지 보낼 수 없을 만큼 느리게 보내는 올리기 요청이 있다.
- When: 그 요청을 서버에 보낸다.
- Then: 서버는 파일을 보관하지 않고 요청을 끝내며, 그 파일은 목록에 나타나지 않는다.
- 작성하지 않는 이유: 실행 시간 한도는 Supabase가 서버 함수에 거는 제한이라 앱 경계에서 관찰할 수 없고, 앱은 이 거절을 다른 실패와 같이 다룬다(TC-FILE-STORAGE-DATA-006). 자동화하려면 실제 서버 함수에 한도를 넘는 느린 요청을 보내고 보관 여부를 조회하는 서버 테스트 환경이 필요하다.

### TC-FILE-STORAGE-DATA-026: 이어서 불러오는 사이에 새 파일이 올라와도 중복이나 누락이 없다

- 근거: `common > data > 목록 요청`
- Given: 계정 A가 첫 요청으로 파일 20개를 받았고, 그 뒤 계정 A의 다른 기기에서 새 파일이 올라왔다.
- When: 받은 20개 중 마지막 파일을 기준으로 이어서 불러온다.
- Then: 이미 받은 파일이 다시 오지 않고, 첫 요청 때 받지 않은 파일이 빠지지 않으며, 새로 올라온 파일은 이어서 불러온 결과에 나타나지 않는다.
- 작성하지 않는 이유: 마지막 파일을 기준으로 다음 파일을 고르는 것은 서버의 목록 처리라 앱 경계에서 관찰할 수 없다. 앱이 마지막 파일을 기준으로 요청하는 것은 TC-FILE-STORAGE-DATA-002가 확인한다. 자동화하려면 실제 서버에 파일을 올리며 목록을 조회하는 서버 테스트 환경이 필요하다.
