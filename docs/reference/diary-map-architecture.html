한눈에 보기 — 3층 구조

지도 연동은 세 층으로 나뉜다. 위 두 층은 commonMain에 있고 플랫폼 SDK를 전혀 모른다. SDK를 아는 코드는 맨 아래 층뿐이며, 그 층은 expect 두 개(NaverMap, GoogleMap)로만 위층과 만난다.

① 배치·전환 층
DiaryMap → DiaryMapOverlayLayout / DiaryMapCardLayout + DiaryMapProviderSelector / DiaryMapProviderTabRow
전환 컨트롤을 어디에 둘지만 정한다. 지도 내용은 map: @Composable () -> Unit 슬롯으로 받는다.
② 상태·계약 층
DiaryMapState + DiaryMapCamera · DiaryMapCoordinate · DiaryMapBounds · DiaryMapPin · DiaryMapProvider
지도가 알려오는 사실과 화면이 내리는 명령이 모두 이 한 객체를 지난다. DiaryMapContent가 state.provider로 ③을 고른다.
③ SDK 연동 층
naver google internal expect fun NaverMap(...) · internal expect fun GoogleMap(...)
androidMain · iosMain · jvmMain · wasmJsMain이 각각 actual을 낸다. 시그니처는 넷 모두 같다 — modifier, state, onSpotClick, onPinClick.

두 제공자의 구현이 같은 계층에 나란히 있다는 점이 핵심이다. 제공자 전환은 상태 한 칸(state.provider)이 바뀌면 DiaryMapContent의 when이 다른 컴포저블을 부르는 것으로 끝나고, 카메라·지점·핀은 DiaryMapState에 그대로 남아 새 지도가 이어받는다. 

// DiaryMapContent.kt — 전환의 전부
when (state.provider) {
    DiaryMapProvider.NAVER  -> NaverMap(state = state, modifier = modifier, onSpotClick = onSpotClick, onPinClick = onPinClick)
    DiaryMapProvider.GOOGLE -> GoogleMap(state = state, modifier = modifier, onSpotClick = onSpotClick, onPinClick = onPinClick)
}

State 관리 — DiaryMapState

@Stable public class DiaryMapState 하나가 지도의 모든 상태를 소유한다. 모든 프로퍼티는 mutableStateOf이고 setter가 전부 private set이다. 바꾸는 길은 의도가 이름에 드러난 함수뿐이다.

상태와 공개 범위

이름공개누가 쓰는가바뀌는 계기
providerpublic전환 컨트롤, DiaryMapContentselect(provider)
spotpublic지점 마커 효과selectSpot(coordinate?)
pinspublic핀 마커 효과updatePins(pins)

coordinatepublic (파생)화면 (보고 있는 위치)camera에서 계산

camera가 internal인 것이 이 설계의 중심이다. 확대 수준까지 포함한 카메라는 지도 표시 계층의 관심사이고, 화면에는 필요한 만큼만(coordinate, bounds) 공개한다.

두 방향의 흐름

지도와 앱은 서로 반대 방향으로 딱 두 갈래로만 대화한다. 이 두 갈래를 구분하는 것이 DiaryMapState를 읽는 열쇠다.

↑ 지도 → 앱
(사실 보고)
사용자가 지도를 움직임 → SDK의 카메라 정지 알림 → state.moveCamera(camera) → camera와 bounds가 갱신 → 화면이 snapshotFlow { state.bounds }로 읽어 조회를 다시 함.
지점·핀 누르기는 상태를 거치지 않고 onSpotClick / onPinClick 콜백으로 바로 나간다. 무엇을 할지는 배치한 화면이 정하기 때문이다.
↓ 앱 → 지도
(명령)
화면이 state.moveTo(coordinate) → camera를 먼저 갱신하고 moveCommandChannel.trySend(moved) → 플랫폼의 ...MoveCameraEffect가 moveCommand를 collect해 SDK 카메라를 옮김.
지점과 핀은 상태(spot, pins)를 갱신하고, 각 플랫폼 효과가 snapshotFlow로 따라간다.

왜 위치 이동만 상태가 아니라 채널인가

moveTo는 같은 좌표로 두 번 부르면 두 번 움직여야 하는 명령이다. 상태로 두면 값이 같아 두 번째가 사라진다. 그래서 Channel(Channel.CONFLATED) + receiveAsFlow()를 쓴다. 같은 값을 반복해도 매번 전달되고, 아직 소비되지 않은 명령이 쌓여 있으면 마지막 하나만 남는다 — 화면 이동은 최신 목적지만 의미가 있으므로 이 합치기가 맞다.

대신 moveTo는 camera도 즉시 갱신한다. 명령을 받을 지도가 아직 붙지 않았을 수 있고, 그때는 새로 만들어지는 지도가 camera를 초기 위치로 읽어 같은 결과에 도달한다. 확대 수준은 보고 있던 값을 유지하고, 보고 있던 카메라가 없으면 NEIGHBORHOOD_ZOOM = 15.0을 쓴다.

moveTo는 bounds를 건드리지 않는다. 보이는 영역은 지도가 실제로 그려 본 뒤에만 알 수 있는 값이므로, moveCamera로 지도가 알려올 때만 바뀐다.

보이는 영역의 수명

moveCamera는 bounds = camera.bounds로 덮어쓴다. 즉 보이는 영역이 없는 카메라가 오면 영역은 null로 돌아간다. SDK가 최초 로드에서 보이는 영역을 주지 못하는 경우가 실제로 있어(아래 대조표), 이 정책을 명시적으로 테스트로 고정해 두었다 (TC-DIARY-MAP-DOMAIN-034, 035).

저장과 복원

rememberDiaryMapState(initialProvider = NAVER, initialCoordinate = null)은 rememberSaveable(saver = DiaryMapState.Saver)이다. mapSaver로 다음 값을 저장한다.

저장하는 것키복원 방법
선택한 제공자providerDiaryMapProvider.valueOf(name) — 이름으로 저장하므로 enum 선언 순서에 의존하지 않는다
보고 있던 카메라latitude, longitude, zoom세 값이 모두 있을 때만 moveCamera로 되돌린다
보이는 영역boundsSouth, boundsNorth, boundsWest, boundsEast넷 중 하나라도 없으면 영역 없음으로 복원
고른 지점spotLatitude, spotLongitudeinitialSpot으로 생성자에 전달
pins는 저장하지 않는다. 핀은 화면이 자기 데이터에서 파생시켜 updatePins로 다시 밀어 넣는 값이므로, 복원해 두면 오히려 낡은 핀이 한 프레임 남는다.

복원 경로는 initialCoordinate를 쓰지 않는다. 복원할 카메라가 있으면 그것이 초기 위치보다 항상 우선이고, 초기 위치는 지도가 처음 만들어질 때 한 번만 쓰이는 값이다.

제공자를 바꿔도 이어지는 것

select는 provider 한 칸만 바꾼다. camera·spot·pins·bounds는 같은 객체에 남아 있으므로, 새 제공자의 지도는 state.camera를 초기 카메라로 읽어 보고 있던 자리에서 시작한다. 네이버 → Google → 네이버로 돌아와도 마지막으로 본 카메라가 이어진다(테스트로 고정).

지도 인스턴스를 지키는 두 장치

지도는 만들 때마다 SDK 초기화·타일 로드가 다시 일어나는 무거운 객체다. DiaryMap은 그것이 헛되게 다시 만들어지지 않도록 두 장치를 쓴다.

movableContentOf — 배치가 바뀌어도 같은 지도

// DiaryMap.kt
val map = remember(state, dispatchSpotClick, dispatchPinClick) {
    movableContentOf {
        DiaryMapContent(state = state, modifier = Modifier.fillMaxSize(), onSpotClick = …, onPinClick = …)
    }
}

when (layout) {
    DiaryMapLayout.OVERLAY -> DiaryMapOverlayLayout(state = state, modifier = modifier, map = map)
    DiaryMapLayout.CARD    -> DiaryMapCardLayout(state = state, modifier = modifier, map = map)
}

movableContentOf로 감싸면 지도가 composition 트리의 다른 자리로 옮겨져도 상태와 노드가 살아서 이동한다. 배치가 OVERLAY↔CARD로 바뀌거나 상위 트리가 재구성돼도 지도는 그대로다.

rememberDispatch — 콜백 신원 고정

위 remember의 키에 콜백이 들어간다. 호출자가 onPinClick = { … }처럼 매번 새 람다를 넘기면 키가 매번 달라져 movableContentOf가 다시 만들어지고, 지도도 다시 만들어진다. 그래서 콜백을 신원이 고정된 래퍼로 감싼다. 

// DiaryMap.kt — 신원은 고정, 내용은 최신
private fun <T> rememberDispatch(callback: ((T) -> Unit)?): ((T) -> Unit)? {
    val latestCallback by rememberUpdatedState(callback)
    val stableCallback: (T) -> Unit = remember { { value -> latestCallback?.invoke(value) } }

    return stableCallback.takeIf { callback != null }
}

takeIf가 중요하다. 콜백을 쓰는지 여부는 SDK 연동에 실제로 영향을 준다 — 지점 선택을 쓰지 않는 화면에서는 지도 클릭 리스너 자체를 달지 않고, 핀 선택을 쓰지 않으면 마커를 clickable = false로 만든다. 그래서 null은 null로 유지되어야 하고, 그 판정만 매 재구성마다 다시 계산한다.

제공자 전환 컨트롤과 배치

DiaryMapLayout.OVERLAY — Android · iOS

Box 안에서 지도가 전체를 채우고, SingleChoiceSegmentedButtonRow가 Alignment.TopCenter에 componentSpacing 여백을 두고 떠 있다.

DiaryMapLayout.CARD — JVM · wasmJs

Card 안에서 PrimaryTabRow가 위쪽에 붙고, 지도가 weight(1F)로 남은 영역을 채운다. 겹치지 않는다.

기본값은 public expect val defaultDiaryMapLayout으로 플랫폼이 정한다. Android·iOS는 OVERLAY, JVM·wasmJs는 CARD다. JVM과 웹의 지도는 Compose가 아닌 별도 표시 계층(네이티브 웹뷰, DOM 요소)에 그려져 Compose 컴포저블을 그 위에 겹칠 수 없기 때문이다. 배치한 화면이 layout 파라미터로 덮어쓸 수도 있다.

전환 항목의 순서는 enum 선언 순서가 아니라 diaryMapProviderList가 소유한다(네이버, Google). 두 컨트롤은 문구·접근성 이름을 DiaryMapProviderLabel에서 공유하고, 컨트롤 전체에 contentDescription을 단다.

플랫폼별 연동

탭을 눌러 플랫폼을 고르면 그 플랫폼의 두 제공자 구현이 나란히 나온다.

두 제공자의 성격이 가장 크게 갈리는 플랫폼이다. Google 지도는 maps-compose라는 선언형 래퍼가 있어 마커까지 컴포저블로 쓰고, 네이버 지도는 명령형 View라 AndroidView로 감싸고 모든 반영을 효과로 직접 쓴다.

naver MapView + AndroidView

  • 뷰 생성 — rememberNaverMapViewWithLifecycle(camera)가 MapView(context, naverMapOptions(camera))를 remember. 초기 카메라와 컨트롤·제스처 옵션을 NaverMapOptions에 한 번에 넣는다.
  • 수명 주기 — LifecycleEventObserver로 onCreate/onStart/onResume/onPause/onStop을 중계하고, onDispose에서 onDestroy. 인스턴스 상태는 rememberSaveable이 들고 있는 Bundle에 onSaveInstanceState로 담는다.
  • 클라이언트 획득 — getMapAsync는 비동기다. rememberNaverMapClient가 결과를 mutableStateOf<NaverMap?>에 담고, 모든 효과는 client == null이면 아무 것도 하지 않고 빠진다. 클라이언트가 붙는 순간 효과가 다시 실행돼 밀린 상태가 한 번에 반영된다.
  • 효과 5개 — ShareCamera(addOnCameraIdleListener → moveCamera, 영역은 client.contentBounds), SelectSpot(setOnMapClickListener), SpotMarker(Marker 하나를 재사용), PinMarkers(Marker 목록 전체 교체), MoveCamera(CameraUpdate.scrollTo).

google maps-compose

  • 지도 — com.google.maps.android.compose.GoogleMap을 그대로 쓴다. MapProperties·MapUiSettings는 remember로 고정.
  • 카메라 — rememberCameraPositionState { state.camera?.let { position = … } }로 초기값을 넣는다. 위로 올리는 쪽은 GoogleMapShareCameraEffect가 snapshotFlow { cameraPositionState.position }을 collect하고, 영역은 projection?.visibleRegion?.latLngBounds에서 얻는다(projection이 아직 없으면 null).
  • 이동 — cameraPositionState.move(CameraUpdateFactory.newLatLng(...)).
  • 클릭 — 컴포저블 파라미터 onMapClick, onPOIClick. 둘 다 같은 onSpotClick으로 접히므로 관심 지점을 눌러도 지점 선택이 된다.
  • 마커 — 지도 content 람다 안에서 state.spot과 state.pins를 직접 읽어 Marker·MarkerComposable을 그린다. 효과가 아니라 선언이므로 목록 교체 코드가 없다.

두 구현 모두 isFinite 확장으로 좌표를 걸러 낸다(filter { pin -> pin.isFinite }). NaN·무한대가 SDK에 들어가면 제공자마다 다르게 깨지므로 경계에서 막는다.

호스트 테스트 제약

실제 지도 SDK는 Robolectric에서 VerifyError로 죽는다. 그래서 지도는 map 슬롯으로 분리돼 있고, androidHostTest는 슬롯에 가짜를 넣어 배치와 전환 컨트롤만 검증한다.

두 SDK 모두 swiftPMDependencies로 가져와 swiftPMImport.DiaryKmp.compose.compose.map 패키지로 보인다. 구조는 대칭이다 — UIKitView로 뷰를 만들고, update에서 뷰 참조를 Compose 상태에 담고, 효과들이 그 참조를 기다린다. 

// 두 제공자가 공유하는 골격
var mapView by remember(state) { mutableStateOf<GMSMapView?>(null) }   // 네이버는 NMFMapView?

SpotMarkerEffect(mapView = mapView, state = state)
PinMarkersEffect(mapView = mapView, state = state, …)
MoveCameraEffect(mapView = mapView, moveCommand = state.moveCommand)

UIKitView(
    factory = { … 초기 카메라·옵션·delegate 설정 … },
    modifier = modifier,
    update = { view -> mapView = view },              // 붙는 순간 효과들이 다시 실행된다
    onRelease = { view -> … delegate 해제 …; mapView = null },
)

naver NMFNaverMapView

  • 뷰 — NMFNaverMapView가 컨트롤 표시(showCompass, showScaleBar, showZoomControls, showIndoorLevelPicker, showLocationButton)를, 내부 mapView가 제스처·초기 카메라를 담당한다.
  • delegate 2개 — NaverMapCameraDelegate(NMFMapViewCameraDelegateProtocol.mapViewCameraIdle → state.moveCamera, 영역은 mapView.contentBounds)와 NaverMapTouchDelegate(NMFMapViewTouchDelegateProtocol의 didTapMap → onSpotClick). 지점 선택을 쓰지 않으면 touch delegate를 아예 만들지 않는다.
  • 카메라 델리게이트 등록 — addCameraDelegate / removeCameraDelegate로 짝을 맞춘다.
  • 마커 — NMFMarker + NMF_MARKER_IMAGE_BLACK에 iconTintColor로 색을 입히고 captionText로 라벨. 즉 제공자 기본 핀에 색을 얹는 방식이다.
  • 핀 누르기 — touchHandler = { true }로 소비해 제공자 정보 창이 열리지 않게 한다.

google GMSMapView

  • delegate 1개 — GoogleMapDelegate가 GMSMapViewDelegateProtocol의 네 콜백을 모두 구현한다: idleAtCameraPosition(→ moveCamera), didTapAtCoordinate, didTapPOIWithPlaceID, didTapMarker.
  • 보이는 영역 — projection.visibleRegion()의 네 꼭짓점에서 minOf/maxOf로 계산한다. 회전·기울임 때문에 사각형이 축에 정렬되지 않으므로 네 점을 다 봐야 한다.
  • 핀 식별 — GMSMarker.userData에 Uuid.toString()을 넣고, 탭 콜백에서 Uuid.parseOrNull로 되돌린다. userData가 문자열만 실을 수 있어 이 경계에서만 문자열로 바꾼다.
  • 핀 모양 — 공용 벡터 경로를 createPinMarkerImage로 Skia 비트맵 → PNG → UIImage로 만들어 iconView에 넣는다. 라벨이 있으면 UIImageView + UILabel을 UIView 컨테이너에 쌓고 groundAnchor를 이미지 높이 비율로 맞춘다.
  • didTapMarker는 항상 true를 반환해 기본 정보 창을 막는다.

JVM에는 두 제공자의 네이티브 SDK가 없다. 그래서 로컬 HTTP 서버가 웹 지도 문서를 내려 주고, 네이티브 웹뷰가 그것을 띄우는 구조를 쓴다. 제공자별로 다른 것은 문서와 서버 라우팅뿐이고, 웹뷰 임베드·명령·메시지 수신은 MapWebView가 공유한다.

① 서버 기동
produceState가 withContext(NonCancellable + Dispatchers.IO)에서 MapHttpServer.start를 부른다. Ktor CIO, 127.0.0.1, 포트 0(임의) → resolvedConnectors()로 실제 포트를 읽어 http://localhost:포트/를 만든다. 기동·종료가 호출 스레드를 블로킹하므로 AWT EDT에서 돌리지 않는다. 기동 중 취소되면 닫을 수 없는 서버가 생기므로 기동은 NonCancellable이다.
② 문서 생성
리소스의 naver-map.html / google-map.html 템플릿에서 플레이스홀더를 치환한다 — {{DIARY_MAP_CAMERA}}, {{DIARY_MAP_SPOT}}, {{DIARY_MAP_SPOT_SELECTABLE}}, {{DIARY_MAP_PINS}}, {{DIARY_MAP_PIN_SELECTABLE}}, {{DIARY_MAP_PIN_MARKER}}, 그리고 인증 키. 키가 [A-Za-z0-9_-]+에 맞지 않으면 문서를 만들지 않고 null을 반환해 서버를 아예 띄우지 않는다.
③ 웹뷰 임베드
WebKitWebViewPanel(library:webkit, WKWebView를 FFM으로 다룬다)에 loadUrl하고 SwingPanel로 배치한다.
④ 앱 → 문서
evaluateJavaScript로 문서의 전역 함수를 부른다: window.diaryShowSpot(lat, lng), window.diaryClearSpot(), window.diarySetPins([...]), window.diaryMoveTo(lat, lng). 모든 호출은 evaluateWhenReady가 isDocumentReady를 first { it }로 기다린 뒤에 나간다.
⑤ 문서 → 앱
문서가 window.ipc.postMessage(JSON.stringify(...))로 보내고, MapWebViewDrainMessageEffect가 200ms마다 drainIpcMessages()로 모아 toMapMessageOrNull()로 파싱한다. ready → 준비 완료, camera → state.moveCamera, click → onSpotClick, pinClick → onPinClick. 파싱은 전부 관용적이다. 알 수 없는 type, 빠진 필드, 유한하지 않은 수는 null로 떨어져 무시된다.

ready는 문서에서 두 번 보낸다 — 스크립트 실행 직후 한 번, 지도 초기화가 끝난 뒤 한 번. 웹뷰의 IPC 브리지가 언제 붙는지가 문서 로드 시점과 맞지 않을 수 있어 양쪽에서 알린다.

naver SDK를 서버가 가공해서 내려준다

네이버 지도 JS SDK는 http://localhost 문서에서 그대로 동작하지 않는다. 그래서 NaverMapResourceLoader가 SDK를 서버 쪽에서 내려받아 두 곳을 바꿔 /naver-maps.js로 다시 제공한다.

  • JSONP → 같은 출처 프록시: o.src=e(스크립트 태그 주입)를 fetch("/naver-proxy?url=…") 후 eval로 바꾼다.
  • 보안 컨텍스트 강제: et=tt||0===t.location.protocol.indexOf("https")를 et=true로 바꾼다.
  • 두 치환은 replaceRequired로 대상 문자열이 없으면 예외다. SDK가 바뀌어 패치가 먹지 않는데 조용히 넘어가지 않게 한다("Unsupported Naver Maps SDK").
  • /naver-proxy는 oapi.map.naver.com, map.pstatic.net, nrbe.pstatic.net만 허용하고, 자격 정보·프래그먼트가 붙은 URL을 거부하며 항상 HTTPS 기본 포트로 정규화해 중계한다. 실패는 502.
  • 문서의 원본 SDK <script>는 type="application/naver-map-config"로 두어 브라우저가 실행하지 않고, 실제 코드는 /naver-maps.js가 내려준다.

google 문서 하나로 끝난다

Google Maps JS는 http://localhost에서 그대로 동작하므로 프록시가 없다. GoogleMapHttpServer는 / 하나만 라우팅하고, 문서가 maps.googleapis.com을 loading=async&callback=initGoogleMap으로 직접 불러온다.

초기 카메라가 없을 때의 확대 수준을 Math.ceil(Math.log2(viewportSize / 256))으로 계산해 세계 지도가 영역을 채우게 한다. wasm 구현도 같은 식을 쓴다.

웹에서는 SDK가 이미 페이지에 있다. app/wasm의 index.html이 두 SDK를 async로 불러오고, 준비 시점을 프라미스로 노출한다. 

// app/wasm/src/commonMain/resources/index.html
window.diaryNaverMapReady = new Promise((resolve) => { window.diaryNaverMapLoaded = resolve; });
window.diaryGoogleMapReady = new Promise((resolve) => { window.diaryGoogleMapLoaded = resolve; });
// …maps.js?ncpKeyId=${naverMapNcpKeyId}&callback=diaryNaverMapLoaded
// …maps/api/js?key=${googleMapApiKey}&loading=async&callback=diaryGoogleMapLoaded

Kotlin 쪽은 지도 조작 객체를 js("(() => { … })()")로 만들고, 그것을 external interface로 타입만 붙여 다룬다. JS 클로저가 지도·마커·옵저버를 들고 있고, Kotlin은 인터페이스의 여섯 함수만 부른다. 

// NaverMapState.kt / GoogleMapState.kt — 두 파일이 같은 모양이다
internal external interface NaverMapState : JsAny {
    fun attach(element: HTMLElement)
    fun release(element: HTMLElement)
    fun showSpot(latitude: Double, longitude: Double)
    fun clearSpot()
    fun setPins(pinsJson: String)
    fun moveTo(latitude: Double, longitude: Double)
}
  • DOM 부착 — HtmlElementView로 div(100% × 100%)를 만들고 attach(element). onRelease에서 release(element).
  • 준비 대기 — attach는 await window.diaryNaverMapReady로 SDK를 기다린 뒤, currentElement !== newElement면 그동안 요소가 바뀐 것이므로 중단한다.
  • 크기 0 회피 — ResizeObserver로 clientWidth/Height가 0이 아닐 때 지도를 만든다. 네이버는 이후 리사이즈마다 map.autoResize()를 부르고, Google은 지도가 이미 있으면 즉시 반환한다.
  • 대기 상태 — 지도가 아직 없을 때 들어온 지점·핀·이동은 pendingSpot·pendingPins·pendingCenter에 쌓아 두고, 지도가 만들어지면 applySpot·applyPins·applyCenter로 한 번에 반영한다.
  • 콜백 — Kotlin 람다(onCamera, onSpot, onPin)를 js() 인자로 넘겨 JS에서 직접 부른다. @Suppress("UnusedParameter")가 붙은 것은 컴파일러가 js() 본문의 참조를 보지 못하기 때문이다.
  • 정리 — dispose()가 옵저버 해제, 마커 setMap(null), 지도 정리를 한다. 네이버는 map.destroy()를 부르고 Google은 참조만 버린다(JS SDK에 파괴 API가 없다).

js() 제약이 구조를 정했다

Kotlin/Wasm의 js()는 톱레벨 함수의 본문 전체여야 하고 문자열 보간을 쓸 수 없다. 그래서 지도 객체 전체를 하나의 IIFE 표현식으로 만들고, 값은 인자(options: JsAny, pinsJson: String)로만 건넨다. 옵션에 카메라를 합치는 것도 보간 대신 MapOptions.kt의 Object.assign 헬퍼로 한다.

네이버 웹 지도의 idle은 최초 로드에서 오지 않는다

네이버 지도의 idle은 이동·확대·축소가 끝났을 때만 발생한다. 그래서 지도를 처음 그린 직후에는 보이는 영역이 앱으로 오지 않는다. JVM·wasm 두 구현 모두 Event.once(map, "init", postCamera)로 초기화 직후 한 번 직접 알리고, JVM 문서는 autoResize() 뒤에도 autoResize가 idle을 발생시키지 않으므로 다시 한 번 알린다. 이것은 bounds로 목록을 조회하는 PlaceHome에서 첫 화면이 비는 문제로 드러났던 부분이다.

핀 마커 — 한 모양을 네 방식으로 그린다

핀의 모양·크기는 commonMain의 DiaryMapPinMarker.kt가 단독으로 소유한다. PIN_MARKER_PATH_DATA(물방울 + 가운데 구멍), PIN_MARKER_VIEWPORT_SIZE = 24, PIN_MARKER_SIZE_DP = 32, PIN_MARKER_LABEL_HEIGHT_DP = 16.

환경같은 경로 데이터를 쓰는 방법
Android googlePinMarkerImageVector(ImageVector.Builder + addPathNodes)를 Icon(tint = pin.color)으로. 라벨은 Text. MarkerComposable이 이 컴포저블을 마커 비트맵으로 굽는다.
iOS googlecreatePinMarkerImage가 CanvasDrawScope로 ImageBitmap에 그리고 Skia로 PNG 인코딩 → UIImage. 라벨은 UILabel, 둘을 UIView에 쌓아 iconView로.
JVM · wasmJs (양쪽 제공자)pinMarkerToScriptValue()가 경로·뷰포트·크기·라벨 높이를 JSON으로 넘긴다. 네이버는 <svg> DOM을 만들어 마커 icon.content로, Google은 google.maps.Symbol의 path·scale·labelOrigin으로 쓴다.
Android · iOS naver예외. 공용 모양을 쓰지 않고 제공자 기본 마커(MarkerIcons.BLACK / NMF_MARKER_IMAGE_BLACK)에 iconTintColor로 색을 입힌다. 네이버 SDK의 마커 표현을 그대로 유지한 결정이다.

문자열 경계의 이스케이프

JVM과 wasm은 핀을 JSON 문자열로 건넨다(jvmWasmMain/DiaryMapPinScript.kt). 라벨은 사용자 입력이므로 \, ", <, >, &, U+2028, U+2029, ISO 제어 문자를 모두 \uXXXX로 바꾼다. 색은 #RRGGBB로, 식별 값은 Uuid 문자열로 나간다.

<·>·&까지 막는 이유는 이 JSON이 HTML 문서 안의 <script> 본문에 직접 삽입되기 때문이다. JSON 문법만 지켜도 </script>가 들어가면 문서가 깨진다.

인증 키 배선

키는 어느 환경에서도 저장소에 들어가지 않는다. 모두 local.properties(iOS는 *Local.xcconfig)에서 읽어 빌드 시점에 주입한다. 두 제공자 모두 선언형으로 SDK에 전달되고, 앱 코드가 키를 직접 들고 있는 곳은 iOS Google 하나뿐이다.

소비자 — 누가 어떻게 쓰는가

compose:map은 도메인 모델을 모른다. Place·Coordinate·MapProvider와의 변환은 compose:place가 소유한다(DiaryMapCoordinateMapper, DiaryMapPinMapper, DiaryMapProviderMapper).

쓰는 곳쓰는 기능상태를 만드는 방법
PlaceHome 핀 표시 + 핀 선택 + 보이는 영역 조회 rememberPlaceHomeMapState(uiState)가 key(defaultProvider, initialCoordinate)로 감싸 두 값이 확정된 뒤의 상태를 만든다. PlaceHomeMoveMapEffect가 snapshotFlow { mapState.bounds }를 화면 이벤트로 올린다.
PlaceAdd · PlaceDetail 지점 선택 PlaceFormState.mapState. onSpotClick에서 화면 상태를 먼저 갱신하고 mapState.selectSpot으로 되돌려 준다.
MemoAdd · MemoDetail 장소 카드 핀 표시 + 핀 선택 rememberMemoPlaceMapState(uiState)가 로딩이 끝나기 전에는 null을 반환하고, MemoPlaceMapBox는 null이면 지도를 아예 부르지 않는다.
장소 검색 다이얼로그 핀 표시 + 핀 선택 PlaceSearchDialogState.mapState. 검색 결과를 테마의 primary 색 핀으로 바꿔 updatePins한다.

핀을 밀어 넣는 쪽은 모두 같은 모양이다 — LaunchedEffect(mapState) { snapshotFlow { provider() }.collect { mapState.updatePins(...) } }. rememberUpdatedState로 provider의 최신 값을 읽으므로 효과를 다시 시작하지 않는다. 기본 제공자는 설정(GetDefaultMapProviderUseCase, 설정 화면은 SettingMap)에서 오고 초기 위치는 화면이 정한다 — PlaceHome은 현재 위치를, 메모 장소 카드는 선택된 장소의 좌표를 쓴다. 두 값이 확정되기 전에는 상태를 만들지 않고, 확정된 뒤에는 key(...)로 감싸 값이 바뀔 때만 새로 만든다. 초기 위치는 지도가 만들어질 때 한 번만 적용되는 값이기 때문이다.

SDK 연동 층(androidMain·iosMain·wasmJsMain의 actual과 효과들)에는 자동 테스트가 없다. 실제 지도는 Robolectric에서 VerifyError로 죽고, iOS·wasm은 이 저장소의 테스트 소스셋(jvmTest, androidHostTest) 대상이 아니다. 그래서 공유 가능한 판단은 최대한 commonMain과 JVM 문서 생성 쪽으로 끌어내려 테스트로 덮고, 연동 층에는 SDK 호출만 남기는 방향으로 코드가 나뉘어 있다. 이 문서의 대조표가 그 남은 부분의 대조 검토용이다.
