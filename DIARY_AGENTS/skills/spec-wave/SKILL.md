# Spec Wave

`docs/spec`의 스펙 문서를 작성하거나 갱신한다.

공통 절차는 `DIARY_AGENTS/wave.md`를 따른다. 문서 탐색, 멈추는 조건, 문서에 남기지 않을 내용, 미확정 표기는 그 문서가 소유하고, 충돌·공백 보고 형식은 `DIARY_AGENTS/confirm.md`가 소유한다.

문서 종류별 소유 범위와 `feature`·`domain`·`data` 영역 구분은 `docs/spec/README.md`를 따른다.

## 원칙

스펙은 제품이 보장하는 계약이므로, 작성보다 기존 스펙과의 충돌 식별을 우선한다. 충돌이 있으면 새 스펙을 쓰지 않고 사용자 결정을 받은 뒤 기존 문서를 수정한다.

문서는 기획자와 제품 이해관계자가 읽는다.

## 충돌 판정 기준

관련 문서를 모두 읽고 다음을 찾는다.

- 같은 사용자 행위의 결과가 문서마다 다름
- 같은 진입 조건, 행동 흐름 또는 관찰 가능한 상태가 서로 맞지 않음
- 도메인 규칙, 권한, 제한, 예외 처리, 상태 전이가 모순됨
- 데이터의 생성, 변경, 저장, 동기화, 삭제 흐름이 서로 맞지 않음
- 날짜, 기간, 정렬, 기본값, 노출 조건 같은 정책 값이 문서마다 다름
- 한 문서의 전제가 다른 문서의 요구사항을 불가능하게 만듦

## 영역별 작성 내용

`feature`, `domain`, `data`는 같은 요구사항을 반복하기 위한 구분이 아니다. 같은 규칙을 여러 영역에 쓰지 않고, 실질적인 내용이 있는 영역만 작성한다.

### feature

사용자가 할 수 있는 행동과 외부에서 관찰 가능한 결과를 쓴다.

- 진입 조건과 접근 경로
- 수행할 수 있는 행동, 행동 후 보장되는 결과와 상태 변화
- 성공, 실패, 빈 상태, 처리 중 상태에서 사용자가 계속할 수 있는 행동
- 다음 행동 흐름과 기능 이탈 결과

구현 컴포넌트명이 아니라 사용자가 인식하는 기능명과 행동명을 쓴다.

### domain

`feature`의 결과를 결정하는 판단 기준을 쓴다. 핵심 개념, 기본값, 포함·제외 기준, 제한, 예외, 상태 전이, 노출 조건은 `feature`와 같은 문장으로 반복하지 말고 여기에 남긴다.

- 기능이 성립하기 위한 도메인 개념
- 허용되는 행동과 금지되는 행동, 권한, 제한, 예외, 우선순위
- 상태와 상태 전이 규칙
- 화면 재생성, 앱 재실행, 백그라운드 복귀처럼 실행 경계가 바뀔 때 사용자 진행 상태를 유지하거나 초기화하는 기준
- 기본값, 정렬, 필터, 기간, 노출 조건 같은 정책

`feature`와 구분되는 판단 기준이 없으면 핵심 개념 정의 수준으로 줄이거나 생략한다.

### data

사용자 또는 서비스 데이터의 생성, 변경, 저장, 동기화, 삭제, 복구 흐름이 있을 때만 작성한다.

- 어떤 행동으로 데이터가 생기고, 언제 변경되거나 삭제되는지
- 어떤 기준으로 데이터를 사용자에게 제공하는지
- 로컬 상태와 원격 상태가 사용자에게 어떻게 보이는지
- 동기화, 실패, 재시도, 복구의 사용자 관점 흐름

기능 진입, 대상 선택, 현재 위치 확인처럼 데이터 조작이 없는 스펙에서는 `data`를 생략한다. 테이블, DTO, API 필드는 기획 판단에 필요한 수준으로만 표현한다.

## 다이어그램

표기와 공통 제약은 `DIARY_AGENTS/wave.md`의 `다이어그램`을 따른다. 스펙에서는 다음 내용에 다이어그램을 둔다.

- 조건이 둘 이상 겹쳐 결과가 갈리는 판정 기준. 예: 표시 여부, 색상 선택, 그룹 구성
- 사용자 진행 상태나 데이터 상태의 전이. 예: 로그인 진행, 업로드 대기
- 성공·취소·실패 경로가 서로 다른 처리 순서. 예: 동기화, 원격 호출
- 여러 단계가 정해진 순서로 이어지고 중간에 중단될 수 있는 흐름

다음에는 두지 않는다.

- 화면 배치나 컨트롤 위치. 이는 디자인이 소유한다.
- 목록으로 충분한 열거. 조건과 결과의 조합이 단순히 많을 때는 표를 쓴다.

다이어그램에는 그 스펙이 확정한 조건과 결과만 그린다. 그리다가 정해지지 않은 분기가 드러나면 임의로 채우지 말고 정책 공백으로 알린다.

## 문서 계층화

절차는 `DIARY_AGENTS/wave.md`의 `문서 계층화`를 따른다. 스펙에서는 다음을 공통 스펙으로 분리할 대상으로 본다.

- 두 화면 이상이 같은 사용자 행위와 판정 규칙을 반복하는 경우. 예: 태그 필터, 목록·상세 배치
- 여러 화면이 같은 도메인 개념과 정책을 반복 정의하는 경우. 예: 메모 기간, 대표 태그
- 화면과 무관하게 성립하는 동기화, 조회, 저장 계약이 화면 스펙 안에 들어 있는 경우

분리한 뒤 각 화면 스펙에는 그 화면에만 적용되는 부분만 남기고, 공통 규칙은 `[공통 스펙](...)의 <절>을 따른다` 형태로 참조한다.

## 문체

사용자 행위 중심으로 쓴다.

권장:

```text
사용자는 일기 목록에서 특정 날짜의 일기를 선택할 수 있다.
일기가 없으면 목록에는 빈 상태가 표시된다.
저장에 실패하면 사용자는 작성 중인 내용을 잃지 않고 다시 시도할 수 있다.
```

비권장:

```text
ViewModel은 Repository를 호출한다.
Composable은 StateFlow를 collect한다.
API 응답 DTO를 Entity로 매핑한다.
```

## 완료 전 확인

- 주요 제품 판단 기준이 `domain`에 누락되지 않음
- 사용자 진행 상태가 있는 기능은 화면 재생성, 앱 재실행, 백그라운드 복귀 경계의 정책이 확정됨
