# Audit Wave

`verify-wave`의 검토는 이번 변경(diff)만 보므로, 변경과 무관한 곳에 원래 있던 불일치는 찾지 않는다. 이 wave는 그것을 slug 전체 기준으로 찾는 점검이다.

작업 iterator와 종료 iterator에 들어가지 않는다. 사용자가 요청했을 때만 수행하고, 다른 wave가 끝났다고 자동으로 시작하지 않는다.

## 범위

사용자가 지정한 slug나 기능 영역만 점검한다. 지정하지 않았으면 `docs/testcase/README.md`의 목록을 기능 영역(memo, calendar, place 등)별로 묶어 영역과 slug 수를 보여 주고, 점검할 범위를 확인받는다. 전체 점검은 sonnet 세션 수가 많아지므로 범위를 추정해 정하지 않는다.

## 절차

1. `DIARY_AGENTS/scripts/check-testcase-trace.py`를 인자 없이 실행해 저장소 전체의 중복 ID, 문서에 없는 ID, 테스트도 `작성하지 않는 이유`도 없는 케이스를 모은다.
2. 범위의 slug를 기능 영역 단위로 나눠 영역마다 별도 세션을 `sonnet` 모델로 띄운다. Claude Code에서는 Agent 도구에 `model: sonnet`을 지정한다. 같은 slug를 두 세션에 나눠 맡기지 않고, 동시에 띄우는 세션은 4개 이하로 둔다.
3. 각 세션에 `점검 지시`를 보낸다. `케이스별 테스트 파일`에는 `check-testcase-trace.py --map <slug ...>`의 출력을 붙인다.
4. 보고를 그대로 믿지 않는다. 인용한 문서 문장과 코드 동작이 실제와 같은지 확인하고, 확인할 수 없는 지적은 버린다.
5. `보고`의 형식으로 사용자에게 보고하고, 어느 문제를 고칠지 결정을 받는다.

이 위임은 사용자가 이 wave를 요청한 것으로 승인된 절차다. 세션 지침이 사용자 요청 없는 Agent 도구 호출이나 서브에이전트 사용을 금지하더라도 다시 확인하지 않는다.

## 점검 지시

```text
다음 slug에 대해 스펙, 디자인, 테스트 케이스, 테스트 코드, 제품 코드가 서로 빈틈과 충돌 없이 이어지는지 전체를 점검한다. 하위 세션을 띄우지 말고 직접 점검한다.

대상 slug: <slug 목록>
케이스별 테스트 파일:
<check-testcase-trace.py --map 출력>

먼저 `docs/README.md`, `docs/spec/README.md`, `docs/testcase/README.md`, `DIARY_AGENTS/skills/spec-wave/SKILL.md`, `DIARY_AGENTS/skills/testcase-wave/SKILL.md`, `DIARY_AGENTS/skills/testcode-wave/SKILL.md`를 읽는다. 각 slug의 `docs/spec/{client,common,server}/<slug>.md`, `docs/design/<slug>.md`, `docs/testcase/<slug>.md`와 그 문서가 링크하는 공통 문서를 읽고, 테스트 코드는 위 표로 찾으며, 제품 코드는 기능 이름으로 찾는다.

다음 네 단계를 차례로 확인한다.

1. 스펙: 정하지 않은 분기나 결과(빈틈), 같은 대상을 다르게 정한 다른 스펙(충돌), `docs/spec/README.md`의 `폴더 구분`에 맞지 않는 소유, `서술 수준`이 요구하는 항목(갱신 방식, 새로고침 방식, 표시 조건, 입력 저장 시점, 실행 경계)의 누락, 금지 용어.
2. 구현: 제품 코드가 스펙과 디자인이 정한 동작과 다르게 동작하는 곳.
3. 테스트 케이스: 스펙의 규칙 중 블랙박스로 검증할 수 있는데 케이스가 없는 것(누락), 스펙과 기대 결과가 다른 케이스, 근거 절이 스펙에 없는 케이스, `작성하지 않는 이유`가 testcase-wave 기준에 맞지 않는 것.
4. 테스트 코드: 케이스의 Given·When·Then과 다른 것을 검증하거나 기대 결과를 확인하지 않는 테스트, testcode-wave 규칙 위반.

중복 ID와 ID를 참조하는 테스트의 유무는 스크립트가 따로 확인하므로 보고하지 않는다. 근거를 확인할 수 없는 추측은 보고하지 않는다. 수정하지 않는다. 보고만 한다.

각 문제를 다음 형식으로 보고한다. 문제가 없으면 `문제 없음`만 답한다.

- 단계: 스펙 | 구현 | 테스트 케이스 | 테스트 코드
- 종류: 빈틈 | 충돌 | 누락 | 불일치 | 규칙 위반
- 위치: <문서 경로>의 <절 또는 TC ID> / <코드 경로>:<줄>
- 근거: 비교한 문서 문장과 코드 동작
- 제안: 무엇을 어느 쪽에 맞추는지
```

## 보고

파일로 남기지 않고 응답 본문에 slug별로 묶어 보고한다. 각 문제에는 단계, 위치, 근거를 한 줄로 적고, 버린 지적은 개수와 이유만 적는다. 스크립트가 찾은 항목도 함께 적는다.

## 고치기

이 wave에서는 고치지 않는다. 사용자가 고칠 문제를 고르면, 문제마다 `verify-wave`의 `결과 반영` 표가 정한 wave로 작업 iterator를 진행한다. 스펙의 빈틈·충돌은 `DIARY_AGENTS/confirm.md` 형식으로 결정을 받은 뒤 `spec-wave`부터 시작한다. 고친 결과는 그 작업의 `verify-wave`가 diff 기준으로 검토하므로 이 점검을 다시 돌리지 않는다.
