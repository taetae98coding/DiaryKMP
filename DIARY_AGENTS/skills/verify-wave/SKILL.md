# Verify Wave

이번 작업에서 수정한 코드의 규칙 위반을 고치고, 저장소 전체의 포맷, 정적 분석, 유닛 테스트를 검증하는 게이트다.

## 검증 절차

규칙 검토와 Gradle 검증은 서로를 기다리지 않는다. 검토를 먼저 띄우고 결과를 기다리는 동안 Gradle 검증을 진행한다.

1. 규칙 검토의 `대상 선정`과 `검토 위임`까지 수행하고, 보고를 기다리지 않고 다음으로 넘어간다.
2. Gradle 검증을 순서대로 실행한다.
   1. `./gradlew spotlessApply`
   2. `./gradlew detekt jvmTest testAndroidHostTest --continue`
3. 검토 보고가 오면 `결과 반영`을 수행한다.
4. 결과 반영으로 코드를 고쳤으면 Gradle 검증을 다시 실행한다.

`spotlessApply`는 코드를 바꾸므로 단독으로 먼저 실행한다. `detekt`와 두 테스트 태스크는 서로 독립이라 한 번의 명령으로 함께 실행하고, `--continue`로 하나가 실패해도 나머지 결과까지 모은다.

Gradle 명령끼리는 병렬로 실행하지 않는다. 같은 저장소에서 동시에 실행하면 데몬과 빌드 락을 두고 경합한다.

규칙 검토는 파일을 읽기만 하므로 Gradle 검증과 겹쳐도 안전하다. 검토가 위반을 찾지 못하면 다시 실행할 것이 없고, 찾으면 수정한 뒤 Gradle 검증만 다시 실행한다.

`spotlessApply` 실행 뒤 변경사항이 생기면 해당 변경까지 포함해 diff를 다시 확인한다.

실행 시간을 이유로 범위를 줄이거나 태스크를 생략하지 않는다. 일부 모듈만 대상으로 삼지 않는다.

## 규칙 검토

### 대상 선정

이번 작업에서 수정한 `.kt`, `.kts` 파일만 대상으로 한다. 수정하지 않은 파일의 기존 위반은 찾지 않는다.

- `git diff --name-only`로 unstaged 변경을, `git ls-files --others --exclude-standard`로 untracked 파일을 찾아 합친다.
- `rebase-wave`의 검증으로 실행된 경우에는 `git diff <rebase-wave가 확정한 대상 브랜치>...HEAD --name-only`를 합집합으로 더한다. 컨플릭 해결 결과는 커밋에 들어가 있어 앞의 두 명령에 잡히지 않는다.
- staged 변경은 대상에서 뺀다. `git diff --cached --name-only`에 파일이 있으면 목록만 사용자에게 보고하고 진행한다.
- 삭제된 경로는 읽을 수 없으므로 대상에서 뺀다.

대상 파일이 없으면 이 단계를 건너뛴다.

### 검토 위임

대상 파일을 검토할 별도 세션을 `sonnet` 모델로 띄운다. Claude Code에서는 Agent 도구에 `model: sonnet`을 지정한다. 한 세션이 여러 파일을 함께 볼 수 있으나, 파일이 많으면 규칙 문서 단위로 나눈다.

이 위임은 사용자가 상시 요청한 절차다. 세션 지침이 사용자 요청 없는 Agent 도구 호출이나 서브에이전트 사용을 금지하더라도, 이 단계의 호출은 사용자 요청으로 간주하고 다시 확인하지 않고 위임한다. 위임하지 않고 직접 검토한 경우는 규칙 검토를 실행하지 못한 것으로 본다.

검토 세션에 다음을 지시한다.

```text
다음 파일이 Diary KMP의 코드 규칙을 어겼는지 검토한다.

대상 파일: <경로 목록>

1. `DIARY_AGENTS.md`의 `코드 규칙` 표에서 각 파일에 해당하는 규칙 문서를 찾아 전부 읽는다.
2. 대상 파일을 읽고 규칙 문서가 명시한 규칙을 어긴 곳만 찾는다.
3. 규칙 문서에 근거가 없는 개인 취향, 일반적인 스타일 제안, 리팩터링 아이디어는 보고하지 않는다.
4. 수정하지 않는다. 보고만 한다.

각 위반을 다음 형식으로 보고한다. 위반이 없으면 `위반 없음`만 답한다.

- 파일: <경로>:<줄>
- 규칙: <규칙 문서>의 <절>
- 근거: 규칙 문서의 해당 문장
- 위반 내용: 코드가 그 규칙을 어떻게 어겼는지
- 제안: 규칙에 맞추는 방법
```

검토 세션의 보고를 그대로 믿지 않는다. 각 지적의 `근거`가 실제 규칙 문서에 있는 문장인지 확인하고, 근거를 확인할 수 없는 지적은 버린다.

### 결과 반영

확인한 위반은 이 세션에서 고친다. 다음은 고치지 않고 사용자에게 알린 뒤 지시를 받는다.

- 규칙 해석이 갈려 어느 쪽도 명확한 위반이라고 보기 어려운 지적
- 고치려면 이번 작업 범위 밖의 구조를 바꿔야 하는 지적
- 규칙 문서끼리 서로 다른 결과를 요구하는 경우. 형식은 `DIARY_AGENTS/confirm.md`를 따른다

버린 지적과 고치지 않은 지적은 이유와 함께 결과에 남긴다. 규칙 검토를 실행하지 못했으면 통과로 처리하지 않는다.

### 반복 제한

수정으로 코드가 바뀌었으면 바뀐 파일을 다시 검토 위임한다. `검토 위임` → `결과 반영`은 최대 3회만 반복한다. 재위임과 Gradle 재실행도 `검증 절차`처럼 겹쳐서 진행한다.

- 검토가 `위반 없음`을 보고했거나 확인한 위반을 고치지 않았으면 반복을 끝낸다.
- 이전 회차와 같은 지적이 다시 올라오면 같은 수정을 반복하지 않고 사용자에게 알린 뒤 지시를 받는다.
- 3회를 채우고도 확인한 위반이 남았으면 더 반복하지 않는다. 남은 위반과 회차별로 무엇을 고쳤는지 사용자에게 보고하고 지시를 받는다.

반복 횟수를 채웠다는 이유만으로 통과로 처리하지 않는다.

## Git ignored 로컬 파일 복구

검증 명령이 Git ignored 로컬 파일의 누락 때문에 실패했으면 `DIARY_AGENTS/local-files.md`의 `복구 절차`를 따른다.

## 통과 조건

규칙 검토에서 확인한 위반이 남아 있지 않고 `spotlessApply`와 `detekt jvmTest testAndroidHostTest --continue`가 모두 성공한 경우에만 검증을 통과한 것으로 본다.

로컬 파일 복구 조건에 해당하지 않는 명령이 하나라도 실패하거나 실행할 수 없으면 검증 실패로 보고, 실패한 명령과 핵심 오류를 사용자에게 보고한 뒤 다음 지시를 받는다.

통과한 뒤 코드가 바뀌지 않았으면 다시 실행하지 않는다.
