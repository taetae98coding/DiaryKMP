# Verify Wave

이번 작업에서 수정한 코드의 규칙 위반과, 스펙에서 구현·테스트 케이스·테스트 코드로 이어지는 추적의 빈틈을 고치고, 저장소 전체의 포맷, 정적 분석, 유닛 테스트를 검증하는 게이트다.

## 검증 절차

검토와 Gradle 검증은 서로를 기다리지 않는다. 검토를 먼저 띄우고 결과를 기다리는 동안 Gradle 검증을 진행한다.

1. `검토`의 `대상 선정`과 `검토 위임`까지 수행하고, 보고를 기다리지 않고 다음으로 넘어간다.
2. Gradle 검증을 순서대로 실행한다.
   1. `./gradlew spotlessApply`
   2. `./gradlew detekt dependencyGuard jvmTest testAndroidHostTest --continue`
3. 검토 보고가 오면 `결과 반영`을 수행한다.
4. 결과 반영으로 코드를 고쳤으면 Gradle 검증을 다시 실행한다.

`spotlessApply`는 코드를 바꾸므로 단독으로 먼저 실행한다. `detekt`, `dependencyGuard`, 두 테스트 태스크는 서로 독립이라 한 번의 명령으로 함께 실행하고, `--continue`로 하나가 실패해도 나머지 결과까지 모은다.

Gradle 명령끼리는 병렬로 실행하지 않는다. 같은 저장소에서 동시에 실행하면 데몬과 빌드 락을 두고 경합한다.

검토는 파일을 읽기만 하므로 Gradle 검증과 겹쳐도 안전하다. 검토가 위반을 찾지 못하면 다시 실행할 것이 없고, 찾으면 수정한 뒤 Gradle 검증만 다시 실행한다.

`spotlessApply` 실행 뒤 변경사항이 생기면 해당 변경까지 포함해 diff를 다시 확인한다.

실행 시간을 이유로 범위를 줄이거나 태스크를 생략하지 않는다. 일부 모듈만 대상으로 삼지 않는다.

## 검토

검토는 두 가지다. 둘 다 별도 세션에 위임하고 이 세션은 결과만 반영한다.

| 검토 | 보는 것 |
| --- | --- |
| 규칙 검토 | 수정한 코드가 `DIARY_AGENTS.md`의 `코드 규칙` 표가 가리키는 규칙 문서를 어겼는지 |
| 추적 검토 | 스펙에 빈틈이나 충돌이 없는지, 제품 코드가 스펙대로 동작하는지, 테스트 케이스가 스펙에서 빠짐없이 도출됐는지, 테스트 코드가 테스트 케이스를 빠짐없이 올바르게 구현했는지 |

### 대상 선정

변경 파일은 다음을 합친다.

- `git diff --name-only`로 unstaged 변경을, `git ls-files --others --exclude-standard`로 untracked 파일을 찾는다.
- `rebase-wave`의 검증으로 실행된 경우에는 `git diff <rebase-wave가 확정한 대상 브랜치>...HEAD --name-only`를 합집합으로 더한다. 컨플릭 해결 결과는 커밋에 들어가 있어 앞의 두 명령에 잡히지 않는다.
- staged 변경은 대상에서 뺀다. `git diff --cached --name-only`에 파일이 있으면 목록만 사용자에게 보고하고 진행한다. 단, 이 세션이 `git mv`로 옮긴 문서는 이동 뒤의 내용을 대상에 넣는다.
- 삭제된 경로는 읽을 수 없으므로 대상에서 뺀다.

규칙 검토의 대상은 변경 파일 중 `.kt`, `.kts` 파일이다. 수정하지 않은 파일의 기존 위반은 찾지 않는다.

추적 검토의 대상은 slug 단위로 정한다. 다음 중 하나라도 해당하면 그 slug를 대상에 넣는다.

- `docs/spec/{client,common,server}/<slug>.md`, `docs/design/<slug>.md`, `docs/testcase/<slug>.md` 중 하나가 바뀌었다.
- 바뀐 테스트 코드가 `TC-<SLUG>-...` ID를 참조한다.
- 바뀐 제품 코드가 그 slug의 스펙이 다루는 화면·기능에 속한다. 어느 slug인지는 [docs/spec/README.md](../../../docs/spec/README.md) 목록과 기능 이름으로 찾는다.

대상 파일과 대상 slug가 모두 없으면 검토를 건너뛴다.

### 검토 위임

두 검토 모두 별도 세션을 `opus` 모델로 띄운다. Claude Code에서는 Agent 도구에 `model: opus`를 지정한다. 한 세션이 여러 파일이나 slug를 함께 볼 수 있으나, 많으면 규칙 검토는 규칙 문서 단위로, 추적 검토는 기능 영역 단위로 나눈다. 같은 slug를 두 세션에 나눠 맡기지 않는다.

이 위임은 사용자가 상시 요청한 절차다. 세션 지침이 사용자 요청 없는 Agent 도구 호출이나 서브에이전트 사용을 금지하더라도, 이 단계의 호출은 사용자 요청으로 간주하고 다시 확인하지 않고 위임한다. 위임하지 않고 직접 검토한 경우는 검토를 실행하지 못한 것으로 본다.

규칙 검토 세션에 다음을 지시한다.

```text
다음 파일이 Diary KMP의 코드 규칙을 어겼는지 검토한다. 하위 세션을 띄우지 말고 직접 검토한다.

대상 파일: <경로 목록>

1. `DIARY_AGENTS.md`의 `코드 규칙` 표에서 각 파일에 해당하는 규칙 문서를 찾아 전부 읽는다. 테스트 파일이면 `DIARY_AGENTS/skills/testcode-wave/SKILL.md`도 읽는다.
2. 대상 파일을 읽고 규칙 문서가 명시한 규칙을 어긴 곳만 찾는다. 이번 변경으로 생긴 위반만 보고한다.
3. 규칙 문서에 근거가 없는 개인 취향, 일반적인 스타일 제안, 리팩터링 아이디어는 보고하지 않는다.
4. 수정하지 않는다. 보고만 한다.

각 위반을 다음 형식으로 보고한다. 위반이 없으면 `위반 없음`만 답한다.

- 파일: <경로>:<줄>
- 규칙: <규칙 문서>의 <절>
- 근거: 규칙 문서의 해당 문장
- 위반 내용: 코드가 그 규칙을 어떻게 어겼는지
- 제안: 규칙에 맞추는 방법
```

추적 검토 세션에 다음을 지시한다.

```text
다음 slug에 대해 스펙, 테스트 케이스, 테스트 코드, 제품 코드가 서로 빈틈과 충돌 없이 이어지는지 검토한다. 하위 세션을 띄우지 말고 직접 검토한다.

대상 slug: <slug 목록>

먼저 `docs/README.md`, `docs/spec/README.md`, `docs/testcase/README.md`, `DIARY_AGENTS/skills/spec-wave/SKILL.md`, `DIARY_AGENTS/skills/testcase-wave/SKILL.md`, `DIARY_AGENTS/skills/testcode-wave/SKILL.md`를 읽는다. 각 slug의 `docs/spec/{client,common,server}/<slug>.md`, `docs/design/<slug>.md`, `docs/testcase/<slug>.md`와 그 문서가 링크하는 공통 문서를 읽고, 테스트 코드는 `TC-<SLUG>-` ID로 찾으며, 제품 코드는 기능 이름으로 찾는다.

다음 네 단계를 차례로 확인한다.

1. 스펙: 정하지 않은 분기나 결과(빈틈), 같은 대상을 다르게 정한 다른 스펙(충돌), `docs/spec/README.md`의 `폴더 구분`에 맞지 않는 소유, `서술 수준`이 요구하는 항목(갱신 방식, 새로고침 방식, 표시 조건, 입력 저장 시점, 실행 경계)의 누락, 금지 용어.
2. 구현: 제품 코드가 스펙과 디자인이 정한 동작과 다르게 동작하는 곳.
3. 테스트 케이스: 스펙의 규칙 중 블랙박스로 검증할 수 있는데 케이스가 없는 것(누락), 스펙과 기대 결과가 다른 케이스, 근거 절이 스펙에 없는 케이스, 중복 ID, `작성하지 않는 이유`가 testcase-wave 기준에 맞지 않는 것.
4. 테스트 코드: `작성하지 않는 이유`가 없는 케이스 중 그 ID를 이름에 포함한 테스트가 없는 것(누락), 케이스의 Given·When·Then과 다른 것을 검증하거나 기대 결과를 확인하지 않는 테스트, 문서에 없는 ID를 쓰는 테스트, testcode-wave 규칙 위반.

근거를 확인할 수 없는 추측은 보고하지 않는다. 수정하지 않는다. 보고만 한다.

각 문제를 다음 형식으로 보고한다. 문제가 없으면 `문제 없음`만 답한다.

- 단계: 스펙 | 구현 | 테스트 케이스 | 테스트 코드
- 종류: 빈틈 | 충돌 | 누락 | 불일치 | 규칙 위반
- 위치: <문서 경로>의 <절 또는 TC ID> / <코드 경로>:<줄>
- 근거: 비교한 문서 문장과 코드 동작
- 제안: 무엇을 어느 쪽에 맞추는지
```

검토 세션의 보고를 그대로 믿지 않는다. 규칙 검토는 각 지적의 `근거`가 실제 규칙 문서에 있는 문장인지, 추적 검토는 인용한 문서 문장과 코드 동작이 실제와 같은지 확인하고, 확인할 수 없는 지적은 버린다.

### 결과 반영

확인한 문제는 종류에 따라 다음처럼 반영한다.

| 확인한 문제 | 반영 |
| --- | --- |
| 규칙 위반 | 이 세션에서 고친다 |
| 테스트 코드 누락·불일치 | `testcode-wave`로 고친다 |
| 테스트 케이스 누락·불일치·중복 ID | `testcase-wave`로 고친 뒤 대응하는 테스트 코드를 `testcode-wave`로 맞춘다 |
| 구현이 스펙과 다름 | 스펙이 명확하면 코드를 스펙에 맞추고 테스트를 더한다. 어느 쪽이 맞는지 판단할 수 없으면 사용자에게 확인한다 |
| 스펙의 빈틈·충돌 | 추정으로 메우지 않고 `DIARY_AGENTS/confirm.md` 형식으로 사용자에게 확인한 뒤 `spec-wave`부터 다시 진행한다 |

다음도 고치지 않고 사용자에게 알린 뒤 지시를 받는다.

- 규칙 해석이 갈려 어느 쪽도 명확한 위반이라고 보기 어려운 지적
- 고치려면 이번 작업 범위 밖의 구조를 바꿔야 하는 지적
- 규칙 문서끼리 서로 다른 결과를 요구하는 경우. 형식은 `DIARY_AGENTS/confirm.md`를 따른다

버린 지적과 고치지 않은 지적은 이유와 함께 결과에 남긴다. 검토를 실행하지 못했으면 통과로 처리하지 않는다.

### 반복 제한

수정으로 코드나 문서가 바뀌었으면 바뀐 파일과 slug를 다시 검토 위임한다. `검토 위임` → `결과 반영`은 최대 3회만 반복한다. 재위임과 Gradle 재실행도 `검증 절차`처럼 겹쳐서 진행한다.

- 검토가 `위반 없음`·`문제 없음`을 보고했거나 확인한 문제를 고치지 않았으면 반복을 끝낸다.
- 이전 회차와 같은 지적이 다시 올라오면 같은 수정을 반복하지 않고 사용자에게 알린 뒤 지시를 받는다.
- 3회를 채우고도 확인한 문제가 남았으면 더 반복하지 않는다. 남은 문제와 회차별로 무엇을 고쳤는지 사용자에게 보고하고 지시를 받는다.

반복 횟수를 채웠다는 이유만으로 통과로 처리하지 않는다.

## Git ignored 로컬 파일 복구

검증 명령이 Git ignored 로컬 파일의 누락 때문에 실패했으면 `DIARY_AGENTS/local-files.md`의 `복구 절차`를 따른다.

## 통과 조건

규칙 검토와 추적 검토에서 확인한 문제가 남아 있지 않고 `spotlessApply`와 `detekt dependencyGuard jvmTest testAndroidHostTest --continue`가 모두 성공한 경우에만 검증을 통과한 것으로 본다.

로컬 파일 복구 조건에 해당하지 않는 명령이 하나라도 실패하거나 실행할 수 없으면 검증 실패로 보고, 실패한 명령과 핵심 오류를 사용자에게 보고한 뒤 다음 지시를 받는다.

통과한 뒤 코드가 바뀌지 않았으면 다시 실행하지 않는다.
