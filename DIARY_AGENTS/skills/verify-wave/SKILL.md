# Verify Wave

이번 변경이 만든 규칙 위반과, 스펙·테스트 케이스·테스트 코드·구현 사이의 어긋남을 diff 기준으로 찾아 고치고, 저장소 전체의 포맷, 정적 분석, 유닛 테스트를 검증하는 게이트다.

## 검증 절차

검토와 Gradle 검증은 서로를 기다리지 않는다. 검토를 먼저 띄우고 결과를 기다리는 동안 Gradle 검증을 진행한다.

1. `검토`의 `대상 선정`과 `검토 위임`까지 수행하고, 보고를 기다리지 않고 다음으로 넘어간다.
2. `Gradle 태스크 선정`으로 실행 대상을 정하고 순서대로 실행한다.
   1. `./gradlew spotlessApply` (실행 대상일 때)
   2. `./gradlew <detekt 태스크, dependencyGuard, jvmTest testAndroidHostTest 중 실행 대상> --continue`
3. `Supabase 검사`의 실행 조건에 해당하면 검사를 실행한다.
4. 검토 보고가 오면 `결과 반영`을 수행한다. 고친 파일이 있으면 `재검토`에 따라 같은 검토 세션에 재검토만 이어 보낸다.
5. 반복이 끝나면, 1회차 Gradle 검증 이후 고친 파일이 실행 조건에 해당하는 Gradle 검증과 Supabase 검사를 한 번만 다시 실행한다. 1회차 Gradle 검증이 실패했으면 그 실패를 고친 수정도 여기에 포함한다.
6. `통과 조건`을 만족하면 `DIARY_AGENTS/scripts/verify-stamp.sh record`를 실행한다.

`spotlessApply`는 코드를 바꾸므로 단독으로 먼저 실행한다. 나머지 태스크는 서로 독립이라 한 번의 명령으로 함께 실행하고, `--continue`로 하나가 실패해도 나머지 결과까지 모은다.

Gradle 명령끼리는 병렬로 실행하지 않는다. 같은 저장소에서 동시에 실행하면 데몬과 빌드 락을 두고 경합한다.

검토는 파일을 읽기만 하므로 Gradle 검증과 겹쳐도 안전하다. 저장소 전체 테스트는 아래 모듈의 작은 변경에도 5분 넘게 걸리므로, 검토 회차마다 다시 돌리지 않고 수정이 모두 끝난 뒤 한 번만 다시 돌린다.

`spotlessApply` 실행 뒤 변경사항이 생기면 해당 변경까지 포함해 diff를 다시 확인한다.

### Gradle 태스크 선정

변경 파일은 `검토`의 `대상 선정`과 같은 방법으로 모으되, 삭제된 경로와 staged 변경도 포함한다. `rebase-wave`의 검증으로 실행된 경우에는 컨플릭 해결 파일 목록 대신 `git diff <대상 브랜치>...HEAD --name-only` 전체를 더한다. 컨플릭이 없었어도 옮긴 커밋 전체가 새 base 위에서 컴파일되고 테스트되어야 하기 때문이다. 태스크마다 다음 중 하나라도 해당하면 실행한다.

| 태스크 | 실행하는 경우 |
| --- | --- |
| `spotlessApply` | `.kt`, `.kts` 파일이 바뀌었다 |
| `detekt` | `.kt` 파일, `config/detekt/**`, `build-logic/**`이 바뀌었다. 범위는 아래 `detekt 범위`를 따른다 |
| `dependencyGuard` | `gradle/libs.versions.toml`, `settings.gradle.kts`, `**/build.gradle.kts`, `build-logic/**`이 바뀌었다 |
| `jvmTest`, `testAndroidHostTest` | 아래 제외 경로가 아닌 파일이 하나라도 바뀌었다 |

테스트 제외 경로는 `docs/**`, `DIARY_AGENTS/**`, `DIARY_AGENTS.md`, `site/**`, `supabase/**`, `iosApp/**`, `config/detekt/**`, `app/*/dependencies/**`, `*.md`다. 이 목록에 없는 경로는 테스트 입력으로 본다.

detekt를 뺀 태스크는 저장소 전체를 대상으로 하고 일부 모듈로 좁히지 않는다. 한 모듈의 변경이 그 모듈을 쓰는 다른 모듈의 컴파일과 테스트를 깨뜨릴 수 있고, 바뀌지 않은 모듈은 빌드 캐시가 다시 실행하지 않기 때문이다. 실행 대상이 하나도 없으면 Gradle 검증을 건너뛰고, 건너뛴 태스크를 결과에 남긴다. 결과 반영으로 파일을 고친 뒤에는 고친 파일까지 포함해 다시 선정한다.

#### detekt 범위

detekt는 모듈마다 자기 소스만 검사해 다른 모듈의 결과에 영향을 주지 않으므로 바뀐 모듈만 실행한다. `DIARY_AGENTS/scripts/changed-module-tasks.sh`가 출력한 `:<모듈>:detekt` 태스크를 쓰고, `rebase-wave`의 검증으로 실행된 경우에는 둘째 인자로 대상 브랜치를 넘긴다(`changed-module-tasks.sh detekt <대상 브랜치>`).

스크립트는 삭제된 파일과 모듈 밖의 `.kt`(루트 직속, `build-logic/**`, `iosApp/**` 등)를 뺀다. 지운 파일은 남은 소스에 위반을 만들지 않기 때문이다. 출력이 비면 detekt를 건너뛰고 결과에 남긴다.

`config/detekt/**`나 `build-logic/**`이 바뀌었으면 스크립트 출력과 무관하게, 모든 모듈의 결과가 달라질 수 있으므로 모듈을 붙이지 않은 `detekt`로 저장소 전체를 실행한다.

### Supabase 검사

`Gradle 태스크 선정`과 같은 방법으로 모은 변경 파일에 `supabase/migrations/**`가 있으면 `supabase/scripts/plpgsql-check.sh`를 실행한다. 이 검사는 dev 프로젝트에 트랜잭션을 열어 배포하지 않은 마이그레이션을 적용하고 PL/pgSQL 함수를 검사한 뒤 롤백한다. Gradle을 쓰지 않으므로 Gradle 명령과 겹쳐 실행해도 된다.

`문제 없음`을 출력하고 0으로 끝나야 통과다. 검사가 보고한 오류는 이번 변경이 만든 것이면 고치고, 기존 함수의 오탐이면 스크립트의 제외 조건에 이유와 함께 더한 뒤 사용자에게 알린다.

## 검토

검토는 두 가지이고, 둘 다 **이번 변경(diff)만** 본다. diff 밖에 원래 있던 위반이나 불일치는 찾지 않는다. 둘 다 별도 세션에 위임하고 이 세션은 결과만 반영한다.

| 검토 | 보는 것 |
| --- | --- |
| 규칙 검토 | 바뀐 코드가 `DIARY_AGENTS.md`의 `코드 규칙` 표가 가리키는 규칙 문서를 어겼는지 |
| 추적 검토 | 바뀐 스펙·테스트 케이스·테스트 코드·제품 코드가, 그와 짝을 이루는 나머지 산출물과 어긋나지 않는지 |

### 대상 선정

변경 파일은 다음을 합친다.

- `git diff --name-only`로 unstaged 변경을, `git ls-files --others --exclude-standard`로 untracked 파일을 찾는다.
- `rebase-wave`의 검증으로 실행된 경우에는 `rebase-wave`가 넘긴 컨플릭 해결 파일 목록을 합집합으로 더한다. 리베이스 도중 해결한 결과는 커밋에 들어가 있어 앞의 두 명령에 잡히지 않는다. 컨플릭 없이 옮겨진 커밋은 패치가 그대로라 리베이스 전 검토 결과가 유지되므로 대상에 넣지 않는다. 새 base와 맞지 않아 생긴 문제는 Gradle 검증이 확인한다.
- staged 변경은 대상에서 뺀다. `git diff --cached --name-only`에 파일이 있으면 목록만 사용자에게 보고하고 진행한다. 단, 이 세션이 `git mv`로 옮긴 문서는 이동 뒤의 내용을 대상에 넣는다.
- 삭제된 경로는 읽을 수 없으므로 대상에서 뺀다.

규칙 검토의 대상은 변경 파일 중 `.kt`, `.kts` 파일과 `supabase/migrations/**`, `supabase/functions/**`의 파일이다. 하나도 없으면 규칙 검토를 건너뛴다.

추적 검토의 대상은 변경 파일 중 다음이다. 하나도 없으면 추적 검토를 건너뛴다.

- `docs/spec/{client,common,server}/<slug>.md`, `docs/design/<slug>.md`, `docs/testcase/<slug>.md`
- 테스트 코드. 짝이 되는 slug는 참조하는 `TC-<UUID>`가 있는 테스트 케이스 문서다.
- 사용자가 관찰하는 동작을 바꾼 제품 코드. 짝이 되는 slug는 [docs/spec/README.md](../../../docs/spec/README.md) 목록에서 기능 이름으로 찾는다. 이름 변경, 포맷, 내부 구조만 바꾼 리팩터링은 대상이 아니다.

변경 내용은 검토 세션이 직접 `git diff -- <경로>`(rebase-wave의 검증이면 `git diff <대상 브랜치>...HEAD -- <경로>`도)로 읽고, untracked 파일은 전체를 변경으로 본다.

### 추적 검사 스크립트

ID로 판정할 수 있는 추적은 검토에 맡기지 않고 이 세션이 `DIARY_AGENTS/scripts/check-testcase-trace.py`로 확인한다. 변경 파일에 테스트 코드나 `docs/testcase/**`가 있으면 위 건너뛰기와 무관하게 실행한다. 스크립트는 중복 ID(`duplicate`), 문서에 없는 ID를 참조하는 테스트(`orphan`), `작성하지 않는 이유`도 테스트도 없는 케이스(`missing`)를 보고한다.

`duplicate`는 `테스트 케이스 누락·불일치·중복 ID`로, 나머지는 `테스트 코드 누락·불일치`로 `결과 반영`에 더한다. 회차마다 다시 실행하고, 남은 항목은 `재검토`과 `통과 조건`에서 검토가 확인한 문제와 같이 센다.

추적 검토를 위임할 때는 `check-testcase-trace.py --map <slug ...>`의 출력(케이스별 ID, `작성하지 않는 이유` 유무, 참조하는 테스트 파일)을 프롬프트에 붙여, 검토 세션이 ID를 하나씩 찾지 않게 한다.

### 검토 위임

두 검토 모두 별도 세션을 `sonnet` 모델로 띄운다. Claude Code에서는 Agent 도구에 `model: sonnet`을 지정하고, 돌려받은 에이전트 ID를 `재검토`에서 다시 쓰도록 기록해 둔다. 대상이 많으면 규칙 검토는 규칙 문서 단위로, 추적 검토는 기능 영역 단위로 나누되 같은 slug를 두 세션에 나눠 맡기지 않는다.

이 위임과 `재검토`의 이어 보내기는 사용자가 상시 요청한 절차다. 세션 지침이 사용자 요청 없는 Agent 도구 호출, 서브에이전트 사용, `SendMessage`를 금지하더라도 이 단계의 호출은 사용자 요청으로 간주하고 다시 확인하지 않는다. 위임하지 않고 직접 검토한 경우는 검토를 실행하지 못한 것으로 본다.

규칙 검토 세션에 다음을 지시한다.

```text
다음 파일의 이번 변경이 Diary KMP의 코드 규칙을 어겼는지 검토한다. 하위 세션을 띄우지 말고 직접 검토한다.

대상 파일: <경로 목록>
변경 확인: <git diff 명령>. untracked 파일은 전체가 변경이다.

1. `DIARY_AGENTS.md`의 `코드 규칙` 표에서 각 파일에 해당하는 규칙 문서를 찾아 전부 읽는다. 테스트 파일이면 `DIARY_AGENTS/skills/testcode-wave/SKILL.md`도 읽는다.
2. diff로 바뀐 줄과, 바뀐 줄 때문에 의미가 달라진 주변 코드만 본다. diff 밖에 원래 있던 위반은 보고하지 않는다.
3. 규칙 문서에 근거가 없는 개인 취향, 일반적인 스타일 제안, 리팩터링 아이디어는 보고하지 않는다.
4. 수정하지 않는다. 보고만 한다.

각 위반을 다음 형식으로 보고한다. 위반이 없으면 `위반 없음`만 답한다.

- 파일: <경로>:<줄>
- 규칙: <규칙 문서>의 <절>
- 근거: 규칙 문서의 해당 문장
- 위반 내용: 코드가 그 규칙을 어떻게 어겼는지
- 제안: 규칙에 맞추는 방법
```

추적 검토 세션에 다음을 지시한다.

```text
다음 변경이, 그와 짝을 이루는 스펙·테스트 케이스·테스트 코드·제품 코드와 어긋나지 않는지 검토한다. 하위 세션을 띄우지 말고 직접 검토한다.

대상 파일: <경로 목록>
짝이 되는 slug: <slug 목록>
변경 확인: <git diff 명령>. untracked 파일은 전체가 변경이다.
케이스별 테스트 파일:
<check-testcase-trace.py --map 출력>

diff로 바뀐 부분에서 출발해, 그 부분과 짝을 이루는 곳만 읽는다. 문서 전체나 slug 전체를 감사하지 않는다.

- 스펙 절이 바뀌었으면: 그 절을 `근거`로 하는 케이스가 바뀐 결과를 반영하는지, 새로 생긴 규칙 중 블랙박스로 검증할 수 있는데 케이스가 없는 것이 있는지, 그 절의 동작을 제품 코드가 따르는지. 바뀐 문장에 `docs/spec/README.md`의 `서술 수준`이 금지하는 용어가 있는지.
- 디자인 절이 바뀌었으면: 그 절이 정한 표현을 제품 코드가 따르는지, 스펙에 없는 행동이나 정책을 더하지 않는지.
- 테스트 케이스가 바뀌었으면: `근거` 절이 스펙에 있고 기대 결과가 그 절과 같은지, `작성하지 않는 이유`가 `DIARY_AGENTS/skills/testcase-wave/SKILL.md`의 `블랙박스 테스트 가능성 판정`에 맞는지, 그 ID의 테스트가 바뀐 Given·When·Then을 검증하는지.
- 테스트 코드가 바뀌었으면: 참조한 ID의 케이스와 다른 것을 검증하거나 기대 결과를 확인하지 않는 곳, `DIARY_AGENTS/skills/testcode-wave/SKILL.md` 규칙 위반.
- 제품 코드가 바뀌었으면: 바뀐 동작이 대응하는 스펙·디자인 절과 다른 곳, 바뀐 동작을 검증하는 케이스나 테스트가 없는 곳.

diff 밖에 원래 있던 불일치, 중복 ID, ID를 참조하는 테스트의 유무는 보고하지 않는다. 근거를 확인할 수 없는 추측은 보고하지 않는다. 수정하지 않는다. 보고만 한다.

각 문제를 다음 형식으로 보고한다. 문제가 없으면 `문제 없음`만 답한다.

- 단계: 스펙 | 구현 | 테스트 케이스 | 테스트 코드
- 종류: 빈틈 | 충돌 | 누락 | 불일치 | 규칙 위반
- 위치: <문서 경로>의 <절 또는 TC ID> / <코드 경로>:<줄>
- 근거: 비교한 문서 문장과 코드 동작
- 제안: 무엇을 어느 쪽에 맞추는지
```

검토 세션의 보고를 그대로 믿지 않는다. 규칙 검토는 각 지적의 `근거`가 실제 규칙 문서에 있는 문장인지, 추적 검토는 인용한 문서 문장과 코드 동작이 실제와 같은지 확인하고, 확인할 수 없는 지적은 버린다.

### 결과 반영

확인한 문제는 종류에 따라 다음처럼 반영한다.

| 확인한 문제 | 반영 |
| --- | --- |
| 규칙 위반 | 이 세션에서 고친다 |
| 테스트 코드 누락·불일치 | `testcode-wave`로 고친다 |
| 테스트 케이스 누락·불일치·중복 ID | `testcase-wave`로 고친 뒤 대응하는 테스트 코드를 `testcode-wave`로 맞춘다 |
| 구현이 스펙과 다름 | 스펙이 명확하면 코드를 스펙에 맞추고 테스트를 더한다. 어느 쪽이 맞는지 판단할 수 없으면 사용자에게 확인한다 |
| 스펙의 빈틈·충돌 | 추정으로 메우지 않고 `DIARY_AGENTS/confirm.md` 형식으로 사용자에게 확인한 뒤 `spec-wave`부터 다시 진행한다 |

다음도 고치지 않고 사용자에게 알린 뒤 지시를 받는다.

- 규칙 해석이 갈려 어느 쪽도 명확한 위반이라고 보기 어려운 지적
- 고치려면 이번 작업 범위 밖의 구조를 바꿔야 하는 지적
- 규칙 문서끼리 서로 다른 결과를 요구하는 경우. 형식은 `DIARY_AGENTS/confirm.md`를 따른다

버린 지적과 고치지 않은 지적은 이유와 함께 결과에 남긴다. 검토를 실행하지 못했으면 통과로 처리하지 않는다. 대상이 없어 건너뛴 검토는 실행하지 못한 것으로 보지 않는다.

### 재검토

수정으로 코드나 문서가 바뀌었으면 다시 검토받는다. `검토 위임` → `결과 반영`은 횟수 제한 없이, 검토가 더 이상 확인할 문제를 내지 않을 때까지 반복한다. 회차 사이에는 Gradle 검증을 다시 실행하지 않고, 반복이 끝난 뒤 `검증 절차`의 5단계에서 한 번만 실행한다.

**2회차부터는 새 세션을 띄우지 않고 1회차에 기록한 에이전트 ID로 같은 세션에 이어 보낸다.** Claude Code에서는 `SendMessage`에 그 ID를 넣는다. 그 세션은 이미 읽은 규칙 문서, 스펙, 코드와 이전 지적을 그대로 기억하므로 다시 읽지 않고 수정만 확인한다. 이어 보낼 내용은 다음과 같다.

```text
<n>회차 재검토다. 지난 회차 지적에 대해 다음처럼 반영했다.

- <지적 위치>: 고침 | 고치지 않음(이유) | 버림(이유)

이번 회차에 바뀐 파일: <경로 목록>
변경 확인: <이번 회차 수정만 보이는 git diff 명령 또는 바뀐 줄 범위>

고친 지적이 실제로 해결됐는지, 이번 수정이 새 위반이나 불일치를 만들었는지만 확인한다. 이전 회차에 문제 없다고 본 부분은 다시 감사하지 않는다. 형식은 처음 지시와 같다.
```

- 수정이 1회차 대상에 없던 파일이나 slug에 닿았으면 같은 세션에 그 파일과 slug를 함께 넘긴다. 다른 영역으로 나눈 세션이 맡던 대상이면 그 세션에 보낸다.
- 세션이 끝나 이어 보낼 수 없거나 같은 세션을 이어 쓸 수 없는 에이전트(Codex 등)에서는, 새 세션에 처음 지시와 함께 위 재검토 내용을 붙여 띄운다.
- 검토가 `위반 없음`·`문제 없음`을 보고했거나 확인한 문제를 고치지 않았으면 반복을 끝낸다.
- 이전 회차와 같은 지적이 다시 올라오면 같은 수정을 반복하지 않고 사용자에게 알린 뒤 지시를 받는다.
- 고친 지적이 같은 위치에서 형태만 바꿔 계속 다시 나오면(수정이 다른 지적을 되살리는 왕복 포함) 수렴하지 않는 것이므로, 회차별로 무엇을 고쳤는지 사용자에게 보고하고 지시를 받는다.

검토가 `위반 없음`·`문제 없음`을 보고하기 전에는 통과로 처리하지 않는다.

## 통과 조건

규칙 검토와 추적 검토에서 확인한 문제가 남아 있지 않고 `Gradle 태스크 선정`으로 정한 태스크와 실행 조건에 해당한 `Supabase 검사`가 모두 성공한 경우에만 검증을 통과한 것으로 본다.

명령이 하나라도 실패하거나 실행할 수 없으면 검증 실패로 보고, 실패한 명령과 핵심 오류를 사용자에게 보고한 뒤 다음 지시를 받는다.

`jvmTest`가 `initializationError`로 실패하고 원인에 `org.koin.plugin.hints.Koin_hints_configrelay_`와 `NoClassDefFoundError`가 함께 있으면, 빌드 캐시가 지우거나 이름을 바꾼 Koin 클래스를 참조하는 옛 힌트 클래스를 복원한 것이다. 코드를 고치지 않고 실패한 모듈마다 `./gradlew :<모듈>:compileTestKotlinJvm --rerun-tasks --no-build-cache`로 다시 컴파일한 뒤 `jvmTest testAndroidHostTest --continue`를 한 번 더 실행하고, 그 결과로 통과를 판정한다. 재실행 사실은 결과에 남긴다.

이번 변경과 관계없어 보이는 테스트가 실패하면 `DIARY_AGENTS/scripts/rerun-test.sh <태스크 경로> <테스트 필터>`로 다시 돌려 항상 실패하는지(종료 코드 1), 간헐적으로 실패하는지(3) 가린 뒤 함께 보고한다. 간헐 실패라도 통과로 처리하지 않는다.

통과한 뒤 코드가 바뀌지 않았으면 다시 실행하지 않는다. 통과 기록(`verify-stamp.sh record`)은 작업 트리 전체의 지문이라, 기록한 뒤 파일이 하나라도 바뀌면 `git commit`을 막는 hook이 검증을 다시 요구한다.
