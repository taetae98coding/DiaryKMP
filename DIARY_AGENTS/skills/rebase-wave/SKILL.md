# Rebase Wave

현재 브랜치를 대상 브랜치 위로 리베이스해 컨플릭을 확인하고 해결하는 게이트다. 머지는 하지 않는다.

## 대상 브랜치 확인

사용자가 대상 브랜치를 지정하지 않았으면 리베이스하기 전에 매번 확인한다. `git branch -a`로 후보를 제시하고 사용자가 고른 브랜치만 대상으로 삼는다.

현재 브랜치가 대상 브랜치와 같으면 리베이스할 것이 없으므로 중단하고 보고한다.

여기서 확정한 대상 브랜치는 이후 `merge-wave`가 그대로 쓴다. 다시 확인하지 않는다.

## 선행 조건

1. `git status`로 작업 트리를 확인한다. 커밋되지 않은 변경은 리베이스를 막지 않고 `리베이스`에서 autostash로 안고 간다. untracked 파일은 목록만 보고하고 진행한다.
2. `git fetch origin`으로 원격을 갱신한다.
3. 대상 브랜치에 대응하는 원격 브랜치가 있으면 대상 브랜치를 `--ff-only`로 갱신한다. fast-forward가 되지 않으면 대상 브랜치가 원격과 갈라진 것이므로 갱신하지 않고 보고한 뒤 지시를 받는다.
4. `git rev-parse HEAD`로 리베이스 전 현재 브랜치의 커밋을 기록해 둔다. 이후 보고에 복구 지점으로 쓴다.

## 리베이스

`git rebase --autostash <대상 브랜치>`를 실행한다. 커밋되지 않은 변경은 autostash가 리베이스 전에 stash하고 리베이스가 끝나면 되돌려 놓는다.

컨플릭이 아닌 이유로 실패하면 `git rebase --abort`로 되돌리고 실패한 명령과 핵심 오류를 보고한 뒤 지시를 받는다.

리베이스 대상 커밋의 메시지와 작성자는 바꾸지 않는다. 커밋을 합치거나 나누지 않는다.

대상 브랜치가 이미 현재 브랜치의 조상이어서 옮긴 커밋이 없으면 리베이스는 아무것도 바꾸지 않은 것이므로 `검증`을 건너뛴다.

## 컨플릭 해결

컨플릭은 리베이스 도중과 autostash 복원 중 두 지점에서 날 수 있고, 둘 다 같은 절차로 해결한다.

`git status`와 `git diff`로 충돌 파일과 각 hunk에서 양쪽이 무엇을 바꿨는지 먼저 파악한다. 충돌한 코드가 속한 영역의 규칙 문서를 읽고 그 규칙에 맞게 해결한다.

해결 원칙은 다음과 같다.

- 두 변경의 의도를 모두 보존한다. 한쪽을 버려야 의도가 유지되는 경우가 아니면 한쪽만 남기지 않는다.
- 충돌을 해소하는 데 필요한 범위만 고친다. 리팩터링이나 정리를 함께 하지 않는다.

다음 중 하나에 해당하면 임의로 결정하지 않고 리베이스를 중단한 상태에서 사용자에게 선택을 받는다. 형식은 `DIARY_AGENTS/confirm.md`를 따르고, `근거` 자리에는 비교한 브랜치 이름을 쓴다.

- 양쪽이 같은 대상에 대해 서로 다른 제품 결정이나 정책을 정의한다.
- 어느 쪽을 택해도 다른 쪽의 동작이 사라진다.
- 생성물이나 잠금 파일처럼 손으로 병합하면 안 되고 재생성해야 하는 파일이다.

해결한 파일을 `git add`로 표시하고 `git rebase --continue`로 진행한다. 리베이스는 커밋마다 멈출 수 있으므로 모든 단계가 끝날 때까지 같은 절차를 반복하고, 단계별로 어떤 파일을 어떻게 해결했는지 기록해 리포트에 쓴다.

autostash 복원에서 충돌하면 리베이스 자체는 이미 끝난 상태이고 stash가 남아 있다. 같은 원칙으로 해결하되 `git rebase --continue`를 쓰지 않고, 해결한 파일을 작업 트리에 그대로 둔 뒤 남은 stash 항목을 `git stash drop`으로 정리한다. 이때 커밋을 만들지 않는다.

어떤 커밋이 대상 브랜치에 이미 반영돼 빈 커밋이 되면 `git rebase --skip`을 임의로 실행하지 않고 해당 커밋과 상황을 보고한 뒤 지시를 받는다.

## 검증

리베이스는 코드를 바꾸므로, 리베이스가 끝나면 컨플릭 유무와 관계없이 `verify-wave`로 검증한다.

검증 대상은 리베이스 최종 상태에 autostash로 되돌아온 변경까지 합친 작업 트리다. 리베이스 중간 커밋은 개별로 검증하지 않으므로, 컨플릭 해결로 중간 커밋이 깨졌을 가능성은 이 검증으로 확인되지 않는다.

검증 중 `spotlessApply`로 파일이 바뀌면 그대로 두고, 커밋 범위에 넣는 것은 `commit-wave`가 처리한다.

검증에 실패하면 이 wave를 통과하지 않은 것으로 본다. 실패를 고치기 위한 코드 수정은 직접 진행하지 않고, 수정 대상과 이유를 설명해 승인을 받은 뒤 진행한다.

## 완료 조건

컨플릭 없이 리베이스와 검증을 통과했으면 승인을 받지 않고 끝낸다.

컨플릭을 해결했으면 `리포트`를 보고하고 사용자 승인을 받을 때까지 이 wave를 끝내지 않는다. 승인 없이 다음 단계로 넘어가지 않는다.

## 리포트

컨플릭을 해결했으면 파일로 남기지 않고 응답 본문에 다음 형식으로 보고한 뒤 승인을 기다린다.

```markdown
리베이스 중 컨플릭을 해결했습니다.

- 대상 브랜치: <이름> (<커밋>)
- 현재 브랜치: <이름>, 리베이스 전 <커밋>

1. <파일 경로>
   - 대상 브랜치 변경: ...
   - 현재 브랜치 변경: ...
   - 해결: ...
   - 이유: ...

이어서 진행할지 알려주세요.
```

해결 내용은 파일별로 무엇을 남기고 무엇을 버렸는지 알 수 있게 쓴다. diff 전체를 붙여넣지 않고, 판단이 갈렸던 지점만 설명한다.

## 실패 처리

리베이스 도중 중단하면 `git rebase --abort`로 리베이스 전 상태로 되돌린 뒤 보고한다. `--abort`는 autostash도 함께 되돌린다.

리베이스가 이미 끝난 뒤에 중단하면 `--abort`로 되돌릴 수 없다. 브랜치를 리베이스된 상태로 두고, 선행 조건에서 기록한 리베이스 전 커밋을 복구 지점으로 함께 보고한다. autostash가 아직 복원되지 않았으면 `git stash list`로 남은 항목을 확인해 함께 보고한다. 복구 명령을 임의로 실행하지 않는다.
