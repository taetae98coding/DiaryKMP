# Design Wave

`docs/design`의 디자인 문서를 작성하거나 갱신한다.

공통 절차는 `DIARY_AGENTS/wave.md`를 따른다. 문서 탐색, 멈추는 조건, 문서에 남기지 않을 내용, 미확정 표기는 그 문서가 소유하고, 충돌·공백 보고 형식은 `DIARY_AGENTS/confirm.md`가 소유한다.

디자인과 스펙의 소유 범위는 `docs/design/README.md`를 따른다.

## 원칙

디자인은 스펙이 정의한 사용자 행위와 제품 정책을 화면에서 제공하고 표현하는 방법만 결정한다. 필요한 제품 판단이 스펙에 없으면 디자인으로 추정하지 말고 스펙을 먼저 확정한다.

아직 확정하지 않은 디자인 결정에 명확한 선택지가 있으면 각 선택지의 사용자 경험, 접근성, 적응형 동작 장단점을 설명하고 사용자의 선택을 받은 뒤 작성한다. 이미 확정된 디자인은 스펙이나 새 요구사항과 충돌하거나 사용자가 재검토를 요청한 경우에만 다시 확인한다.

## 읽는 순서

탐색 절차는 `DIARY_AGENTS/wave.md`의 `대상 문서 탐색`을 따른다. 디자인에서는 기존 디자인 문서보다 대상의 기준 스펙 전체와 그 스펙이 참조하는 관련 스펙을 먼저 읽는다.

## 충돌 판정 기준

- 디자인이 스펙에 없는 행동, 결과, 제한 또는 상태 전이를 추가함
- 디자인이 스펙의 행동, 결과, 상태 또는 정책과 다름
- 같은 공통 컴포넌트나 조작이 문서마다 다르게 표현됨
- 화면 구조, 적응형 배치, 크기, 간격 또는 표시 우선순위가 서로 양립할 수 없음
- 로딩·빈 상태·오류·성공 결과의 표현이 관련 화면 사이에서 모순됨
- 같은 문구나 접근성 이름이 문서마다 다름
- 플랫폼이나 입력 장치별 동작이 누락되거나 서로 충돌함

스펙을 그대로 따르면서 디자인 표현만 바로잡을 수 있으면 디자인 문서를 수정한다. 제품 행위나 정책을 바꿔야 해결되는 충돌이면 스펙을 먼저 수정한다.

## 작성 내용

소유 범위는 `docs/design/README.md`의 `문서 소유권`을 따른다. 그 목록에 더해 다음을 빠뜨리지 않는다.

- 컨트롤의 순서와 표시 우선순위
- 시스템 바, 디스플레이 컷아웃, 소프트 키보드와 겹치지 않는 표시 방식
- 플랫폼, 창 크기, 자세와 입력 장치에 따른 표현 차이
- 비활성 상태의 표현

## 공통 디자인 요소 이름 짓기

**두 문서 이상이 같은 시각 값이나 같은 속성 묶음을 쓰게 되면 각 문서에 숫자를 적지 않고 이름을 붙여 공통 문서로 옮긴다.** 각 문서가 값을 따로 들고 있으면 한쪽만 고쳐져 같은 자리의 표현이 어긋나고, 코드도 문서마다 다른 상수를 만들게 된다. 이름이 붙은 요소는 코드에서 같은 이름의 값이나 Style로 관리하므로(`DIARY_AGENTS/rules/compose.md`의 `시각 속성은 Style, 동작과 배치는 Modifier`), 이름은 코드의 식별자가 따라갈 수 있게 한 번 정하면 바꾸지 않는다.

옮길 곳은 요소의 종류로 정한다.

| 종류 | 소유 문서 | 예 |
| --- | --- | --- |
| 여백·간격 하나짜리 값 | `docs/design/dimens.md` | `Bottom Sheet 가로 여백`, `카드 안쪽 여백` |
| 속성이 둘 이상 모인 묶음, 모양·불투명도처럼 여백이 아닌 값 | `docs/design/styles.md` | `Bottom Sheet 선택 줄`, `카드 내용`, `흐림`, `캘린더 아이템 모양` |

이름은 값이 아니라 쓰는 자리와 역할이 드러나게 짓는다. `여백 24`가 아니라 `Bottom Sheet 가로 여백`, `알파 38`이 아니라 `흐림`이다. 같은 값이라도 역할이 다르면 다른 이름을 둔다. `화면 세로 여백`과 `Bottom Sheet 아래 여백`이 모두 `16dp`여도 한쪽을 바꿀 때 다른 쪽이 따라가면 안 되기 때문이다.

공통 문서의 표에는 이름, 속성, 쓰는 곳을 적는다. 묶음의 속성이 `dimens.md`의 값을 쓰면 숫자 대신 그 이름을 링크한다. 각 화면 문서는 그 이름을 링크로 참조하고, 그 화면에서만 다른 차이만 남긴다. 공통 문서의 `이 문서를 참조하는 문서` 목록도 함께 갱신한다.

이 절은 이름을 붙이는 기준만 소유한다. 나눌 때 사용자 결정을 받는 조건과 나누는 절차는 `DIARY_AGENTS/wave.md`의 `문서 계층화`를 따른다. 새 값을 처음 쓰는 화면이 하나뿐이면 그 화면 문서에 두고, 두 번째 사용처가 생길 때 옮긴다.

## 문서 형식

제목은 대상 이름과 종류를 드러내고, 다음 줄에 `기준 스펙` 링크를 둔다. 여러 스펙이 직접적인 기준이면 모두 링크하되 단순 참고 문서는 나열하지 않는다.

```markdown
# MemoAdd 화면 디자인

기준 스펙: [MemoAdd 화면 스펙](../spec/client/memo-add.md)
```

본문은 고정 템플릿을 채우지 말고 실제 디자인 결정 단위로 구성한다. 공통 컴포넌트나 배치 문서가 이미 결정을 소유하면 링크로 참조하고 같은 규칙을 반복하지 않는다.

다이어그램의 표기와 공통 제약은 `DIARY_AGENTS/wave.md`의 `다이어그램`을 따른다. 디자인에서는 화면과 컴포넌트의 영역 분할, 창 크기나 플랫폼에 따라 갈리는 적응형 배치, 조작에 따른 표시 상태 전이에 다이어그램을 둔다. 정확한 수치, 문구와 색상 값은 글이나 표로 남긴다.

## 문체

사용자가 화면에서 보고 조작하는 표현을 현재형으로 쓴다. 구현 클래스, Compose API, 상태 보관 방식, 이벤트 처리 구조는 설명하지 않는다.

권장:

```text
화면 상단에는 제목과 뒤로가기 버튼을 배치한다.
저장 중에는 저장 아이콘을 진행 표시로 바꾼다.
창 너비가 좁으면 목록과 상세 화면을 한 번에 하나만 표시한다.
```

비권장:

```text
Scaffold의 topBar 슬롯에 TopAppBar를 전달한다.
ViewModel의 isLoading이 true이면 CircularProgressIndicator를 렌더링한다.
BoxWithConstraints에서 maxWidth를 읽어 분기한다.
```

크기와 간격처럼 결과가 고정 수치에 의존하는 결정은 단위와 함께 쓴다. 공통 컴포넌트나 플랫폼의 기본값을 쓸 수 있으면 숫자를 만들지 말고 그 기본값을 따른다고 쓴다. 고정 수치가 필요하지만 값이 확정되지 않았으면 사용자 확인이 필요한 디자인 결정으로 다룬다.

## 완료 전 확인

- 모든 기준 스펙 링크가 존재하고 대상과 일치함
- 스펙에 있는 상태의 표현과, 필요한 요소의 정확한 문구·접근성 이름이 누락되지 않음
- 두 문서 이상이 쓰는 여백·모양·불투명도·속성 묶음이 숫자로 반복되지 않고 `dimens.md` 또는 `styles.md`의 이름으로 참조됨
