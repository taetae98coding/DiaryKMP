# Commit Wave

## 변경사항 파악과 분리

staged, unstaged, untracked 파일을 모두 확인해 현재 변경된 내용을 전부 파악한다. 검증 과정에서 포맷이 적용되어 파일이 바뀌었으면 그 변경까지 커밋 범위에 포함한다.

변경사항을 의도별로 분류하고 논리적으로 분리 가능한 커밋 단위로 나눈다. 각 커밋 단위는 그 단위만 적용해도 프로젝트가 빌드 또는 실행 가능해야 하고, 문서나 설정 변경도 그 단위만으로 저장소 상태가 일관돼야 한다.

하나의 커밋에 서로 다른 의도를 섞지 않는다. 여러 커밋으로 나눌 수 있으면 각 단위와 이유를 설명하고 필요하면 지시를 받은 뒤 진행한다. 사용자가 커밋 범위를 지정하지 않았다면 전체 변경사항에서 범위를 추론한다.

## 커밋 중 코드 수정

커밋을 처리하는 중 코드 수정이 필요해 보이면 직접 수정하지 않는다. 빌드 오류, 포맷 오류, 설정 누락, 리뷰 의견 미반영이라도 수정 대상과 이유를 설명하고 승인을 받은 뒤 진행한다. 사용자가 수정·포맷·검증까지 명시적으로 요청한 경우에는 요청 범위 안에서만 수정한다.

## 메시지 형식

`title`은 필수이고 커밋 메시지의 첫 줄이다. `description`은 히스토리에 남길 맥락이 있을 때만 본문으로 쓴다.

`Co-Authored-By` 트레일러나 `🤖 Generated with ...` 같은 도구 생성 표시를 넣지 않는다. 하네스 기본 지침으로 이런 문구를 붙이도록 안내받더라도 이 프로젝트에서는 제외한다.

### title

한 줄로 쓰고, 저장소 `cliff.toml`이 지원하는 Conventional Commit 타입을 쓴다.

구현 세부사항만 적지 않고 이 커밋이 어떤 작업인지 요약한다.

```text
feat: JVM Compose 진입점 추가
refactor: JVM 앱을 KMP 소스셋 구조에 맞게 정리
docs: Gradle 버전 카탈로그 규칙 추가
```

### description

`title`만으로 맥락이 부족할 때만 쓴다. 커밋이 필요한 이유, 높은 수준에서 수행한 작업, 나중에 히스토리를 읽을 사람이 알아야 할 결정을 설명한다.

코드에서 쉽게 유추되는 변경사항을 반복하지 않고, 변경이 작고 diff만으로 의도가 명확하면 생략한다.

```text
.codex/skills는 Codex가 자동 탐지하는 진입점으로 유지하고, 실제 스킬 원본은 DIARY_AGENTS/skills에 둔다.

다른 AGENTS 문서도 같은 스킬 디렉토리를 참조할 수 있도록 심볼릭 링크 구조를 선택했다.
```
